# 결정 기록

작업하면서 내린 판단과 그 이유를 남깁니다. 같은 고민을 다시 하지 않고, 판단이 틀렸을 때 무엇을 고쳐야 하는지 바로 알기 위해서입니다.

**새 결정을 추가할 때:**
- 해당 주제 아래에 날짜와 함께 적습니다.
- 결정을 뒤집으면 원래 항목을 지우지 않고 "→ 변경"을 붙인 뒤 새 항목을 씁니다.

각 항목은 **결정**, **이유**, **틀렸을 때 비용** 순서로 적습니다.

## 제품 방향

### 2026-10-10 · 해커톤 PoC에서 개인 프로젝트로 전환
- **결정:** 심사용 데모가 아니라 직접 쓰면서 다듬는 개인 프로젝트로 운영한다. 쓸 만해지면 실제 서비스로 연다.
- **이유:** 실제 업무 메일을 처리하는 도구가 필요하다.
- **틀렸을 때 비용:** 없음.

### 2026-10-10 · 메일 중심으로 전환
- **결정:** 서비스의 출발점을 "받은편지함의 업무 메일"로 바꾼다. 기존의 목표 입력 방식은 보조 기능으로 남긴다.
- **사용 서비스:** Gmail과 Google 캘린더.
- **이유:** 사용자가 원하는 흐름은 메일 요약 → 할 일 → 기한 알림 → 답장이다.
- **틀렸을 때 비용:** 목표 입력 중심으로 되돌리려면 화면 구성을 다시 해야 한다.

### 2026-10-10 · 새 메일 감지는 90초 주기 확인
- **결정:** Gmail 푸시(Pub/Sub) 대신 주기적으로 확인한다. 감지 부분은 나중에 푸시로 바꿀 수 있게 분리해 둔다.
- **이유:** 로컬에서 바로 동작하고 Google Cloud 추가 설정이 필요 없다.
- **틀렸을 때 비용:** 새 메일 반영이 최대 90초 늦다.

### 2026-10-10 · 답장은 앱에서 승인해야 발송
- **결정:** Agent가 쓴 답장은 승인 카드에서 사용자가 확인 · 편집하고 승인해야만 Gmail로 나간다.
- **이유:** 잘못된 메일이 자동으로 나가면 되돌릴 수 없다.
- **틀렸을 때 비용:** 없음. 6단계에서 구현한다.

### 2026-10-26 · 배포 보류, 로컬 우선
- **결정:** Railway 등에 배포하지 않고 로컬에서 쓰며 다듬는다.
  - 밖에서도 접속해야 하면 Cloudflare Tunnel을 쓴다.
  - 실제 서비스로 열 때 상시 실행 호스팅(Railway, Fly.io 등)을 고른다.
- **이유:**
  - Google 로그인은 `localhost`에서 동작해서 배포 없이 개발할 수 있다.
  - 비용이 들지 않는다.
  - 앱은 상시 프로세스와 PostgreSQL/pgvector가 필요해서 서버리스는 맞지 않는다.
- **틀렸을 때 비용:** PC가 꺼져 있으면 메일 확인이 멈춘다.

### 2026-10-26 · 진행 순서: Gmail 3~6단계 다음 RAG
- **결정:** 메일 → 업무 → 답장 흐름을 먼저 완성하고 RAG를 붙인다.
- **이유:** RAG의 효과가 가장 큰 곳은 답장 작성(6단계)이다. 검색할 자료(업무 메일, 업무 요약)도 3단계부터 쌓인다.
- **틀렸을 때 비용:** 문서 검색 기능이 늦게 나온다.

## 기존 Agent 기능 (2026-10-10)

- **후속 업무 직접 완료:** Agent가 만든 후속 업무만 사용자가 직접 닫을 수 있다. 일반 업무는 Agent가 완료 조건을 판단한다.
- **업무 취소:** `CANCELLED` 상태로 보관하고 기록을 남긴다. 취소된 업무는 무엇으로도 다시 시작되지 않는다.
- **목표 수정:** 수정하는 즉시 Agent가 다시 계획한다.
- **실시간 갱신:** 서버가 변경을 감지해 SSE로 스냅샷을 보낸다(A 방식). 이벤트별 메시지 방식보다 단순하다.

## Google 연결 (1단계, 2026-10-26)

### 권한 이름 해석
- **결정:** Google이 돌려주는 긴 권한 이름(`.../auth/userinfo.email`)을 요청한 `email` 권한과 같은 것으로 인정한다.
- **이유:** 엄격하게 비교하면 실제 연결이 모두 실패한다.
- **틀렸을 때 비용:** 없음.

### 권한이 빠진 연결은 거절
- **결정:** 권한이 빠졌거나 장기 토큰이 없는 연결은 거절한다. 처음 연결하는 경우에만 방금 받은 권한을 Google에서 취소한다.
- **이유:** 이미 연결된 상태에서 재연결이 실패했을 때 권한을 취소하면, 같은 권한을 쓰는 기존 연결까지 끊긴다.
- **틀렸을 때 비용:** 쓰이지 않는 부분 권한이 Google 쪽에 남을 수 있다. Google 계정의 타사 연결에서 지우면 된다.

### 연결 해제
- **결정:** Google 쪽 권한 취소는 실패해도 넘어가고, 로컬 토큰은 반드시 지운다. 저장된 메일 삭제는 사용자가 선택한다.
- **틀렸을 때 비용:** 권한 취소가 실패하면 Google 계정 화면에 연결이 남는다.

### 다른 계정으로 재연결
- **결정:** 동기화 지점을 초기화하고 이전 토큰을 폐기한다. 이전 계정에서 가져온 메일은 지우지 않는다.
- **이유:** 사용자 데이터를 말없이 지우지 않는다.
- **틀렸을 때 비용:** 두 계정의 메일이 목록에 섞인다. 연결 해제 + 메일 삭제로 정리할 수 있다.

### 캐시는 서버 메모리에만
- **결정:** 로그인 확인용 1회용 값과 접근 토큰 캐시는 서버 메모리에만 둔다.
- **이유:** 로컬 단일 서버 기준이다.
- **틀렸을 때 비용:** 서버를 여러 대로 늘리면 공유 저장소로 옮겨야 한다.

## 메일 동기화 (2단계, 2026-10-26)

### 문제 있는 메일 한 통은 건너뛴다
- **결정:** 가져오는 사이 사라졌거나 해석에 실패한 메일은 건너뛰고 다음 메일로 넘어간다.
- **이유:** 메일 한 통 때문에 받은편지함 전체가 멈추면 안 된다.
- **틀렸을 때 비용:** 그 메일은 다시 시도하지 않는다.

### DB 오류는 주기를 멈춘다
- **결정:** DB 오류가 나면 이번 주기를 멈추고 동기화 지점을 전진시키지 않는다.
- **이유:** 메일 유실을 막는다.
- **틀렸을 때 비용:** 같은 오류가 반복되면 동기화가 멈춘 채 오류가 표시된다.

### 건너뛴 메일 기억
- **결정:** 건너뛴 메일 번호를 서버 메모리에 기억한다. 첫 동기화는 받은편지함만 조회한다.
- **이유:** 보낸 메일이 많아도 동기화가 같은 자리에 멈추지 않는다.
- **틀렸을 때 비용:** 서버를 재시작하면 건너뛴 메일을 한 번 더 조회한다(Gmail 사용량 약간).

### Gmail 사용량 한도(403)는 일시 오류
- **결정:** 사용량 한도(403)는 일시 오류로 보고 다음 주기에 다시 가져온다.
- **틀렸을 때 비용:** 없음.

### 마지막 확인 시각
- **결정:** 한 주기를 끝까지 처리했을 때만 갱신한다.
- **이유:** 변경 기록이 만료됐을 때 다시 훑는 기준점을 지킨다.
- **틀렸을 때 비용:** 밀린 메일이 많으면 화면의 시각이 실제보다 늦게 보인다.

### 데모 초기화는 Gmail 데이터를 건드리지 않는다
- **결정:** 데모 초기화는 가상 데이터만 지운다.
- **이유:** 실수 한 번에 실제 메일이 사라지면 안 된다.
- **틀렸을 때 비용:** 없음.

### 남겨 둔 위험
- **내용:** 동기화가 도는 바로 그 순간 다른 계정으로 바꾸면, 새 계정의 최근 메일 일부를 한 번 놓칠 수 있다.
- **이유:** 재연결은 보통 만료 후에 하고, 만료 상태에서는 동기화가 멈춰 있어 드물다.
- **계획:** 동기화 지점을 저장하기 전에 계정 주소를 다시 확인하도록 나중에 고친다.

## 업무 메일 판별과 접수 (3단계, 2026-10-26)

### 기능 스위치 기본값은 꺼짐
- **결정:** `MAIL_TRIAGE_ENABLED`의 기본값을 꺼짐으로 둔다. 실제 메일로 확인하기 전에 사용자의 동의를 받는다.
- **이유:** 켜면 실제 메일 내용이 LLM 공급자로 나간다.
- **틀렸을 때 비용:** 없음.

### LLM 장애는 시도 횟수로 세지 않는다
- **결정:** LLM 장애(한도, 서버 오류, 시간 초과, 인증)가 나면 메일은 "판별 대기", 업무는 "분석 대기"로 두고 시도 횟수를 세지 않는다.
  - 시도 횟수는 LLM이 이상한 응답을 줬거나 예상 밖 오류가 났을 때만 센다.
  - 3회가 되면 자동 처리를 멈추고 "직접 확인" 상태로 둔다.
- **이유:** 설계 문서 4.3절과 7절을 따른다. 장애 몇 분 때문에 실제 업무 메일이 "업무 아님"으로 굳으면 안 된다.
- **틀렸을 때 비용:** 장애가 길면 주기마다 LLM 호출이 한 번씩 실패한다. 비용은 적다.

### 업무 스레드의 새 메일은 판별하지 않는다
- **결정:** 이미 업무가 있는 스레드의 새 메일은 판별 없이 바로 업무 메일로 보고 기존 업무에 붙인다.
- **이유:** "네, 확인했습니다" 같은 짧은 답장은 혼자 보면 업무가 아닌 것처럼 보인다.
- **틀렸을 때 비용:** 없음.

### 업무를 분석보다 먼저 만든다
- **결정:** 업무를 "메일 분석 대기" 상태로 먼저 만들고, 그다음 분석한다.
- **이유:** 분석이 실패해도 메일이 화면에서 사라지지 않는다.
- **틀렸을 때 비용:** 없음.

### "분석 대기"와 "참고용"은 같은 상태값
- **결정:** 둘 다 `PENDING` 상태를 쓰고, `brief.analysis` 값으로 구분한다.
- **틀렸을 때 비용:** 5단계 화면에서 표시 문구만 나누면 된다.

### 취소한 업무는 다시 분석하지 않는다
- **결정:** 사용자가 취소한 업무는 다시 분석하지 않는다.
- **이유:** 사용자의 판단이 우선이다.

### 기한 해석 규칙
- **결정:**
  - 할 일의 기한 표현이 메일 기한 표현과 같으면 메일 기한의 종류(확정 / 추정)를 따른다.
  - 같은 시각이면 메일 기한이 우선이다.
- **이유:** 실제 LLM 확인에서 "다음 주 중"이 확정 기한으로 바뀌는 문제가 발견됐다.
- **틀렸을 때 비용:** 같은 시각의 확정 할 일 기한이 추정으로 보일 수 있다.

### 수신 시각이 없으면
- **결정:** 저장 시각을 기준으로 기한을 계산한다.
- **틀렸을 때 비용:** 상대 날짜가 동기화 지연만큼 어긋날 수 있다.

## 개발 방식

### 작업 브랜치
- **결정:** 기능마다 브랜치를 만들고 CI가 통과하면 `main`에 병합한다. 혼자 작업하므로 PR은 생략한다.

### 브랜치 정리 권한
- **결정:** 병합된 로컬 브랜치 삭제(`git branch -d`)는 확인 없이 허용한다. 원격 브랜치 삭제는 매번 확인한다.

### 테스트는 실제 설정을 읽지 않는다
- **결정:** 테스트는 실제 `backend/.env` 값을 읽지 않도록 환경을 고정한다. 실제 LLM 확인은 `RUN_LLM_SMOKE=1`일 때만 가상 데이터로 실행한다.

### 배포 전 확인
- **결정:** 배포 전에는 반드시 로컬 서버를 띄워 브라우저에서 바뀐 기능을 직접 눌러 확인한다.
