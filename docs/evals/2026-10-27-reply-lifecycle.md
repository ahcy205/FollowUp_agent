# 6단계 정확도 측정 — 답장 · 업무 생애 (설계 9절)

- 날짜: 2026-10-27
- 모델: Gemini — 기본 `gemini-3.5-flash`, 분석(`structured`) `gemini-3.1-flash-lite`, 분당 5회(`LLM_RPM_LIMIT`)
- 데이터: 가상 메일 25건(`backend/smoke/reply_cases.py`). 회사 · 사람은 지어낸 것이고 주소는 `.example`. 실제 메일은 쓰지 않았다.
- 실행: `cd backend && PYTHONUTF8=1 RUN_LLM_SMOKE=1 ../.venv/Scripts/python -m pytest smoke/test_reply_lifecycle_smoke.py -v -s` (1회 약 5분)
- 측정 대상은 실제 함수 전체다(LLM 응답 + 코드 거르기). 변경 감지는 `run_analysis`, 판단은 `analyze_into_task`(후보 + `judge_related`),
  초안은 `generate_draft` + `draft_warnings`. 메모리 DB에서 사례마다 사용자를 따로 만든다.

## 세는 방법

- **변경 감지:** 사례마다 정답 항목(바뀐 사실과 상태: 반영 · 질문 · 제안)을 정해 둔다.
  - 맞음: 그 사실이 정답 상태로 기록됨(제목 · 요약 · 요청 중 어디에 반영돼도 같은 사실이면 한 번으로 센다).
  - 놓침: 기록되지 않음.
  - 잘못: 질문 · 제안을 확정으로 반영, 인용된 옛 값 · 주입 문장 값을 반영, 정답에 없는 기한 반영, "변경 없음"이 정답인데 반영.
    질문을 "~ 가능 여부 회신" 같은 할 일로 받은 것은 확정으로 본 것이 아니므로 잘못이 아니다.
  - 기타: 답장 필요(needs_reply) · "답장 필요 없음" 표시(thanks_email_id)가 정답과 다른 수.
- **다른 스레드 판단:** 정답 후보(또는 "관계 없음")와 같으면 맞음, 정답이 있는데 제안 안 함은 놓침, 관계 없는데 제안하거나 다른 업무를 고르면 잘못.
- **초안:** `draft_warnings`의 근거 없는 숫자 · 날짜(`unsupported`)와 스레드 밖 연락처, 빈칸이 필요한 사례에 `[[ ]]`이 없는 경우.

**통과 기준(단언):** 잘못 반영한 변경 0건, 근거 없는 숫자 · 날짜 · 연락처가 든 초안 0건, 빈칸이 필요한데 빠진 초안 0건.
놓침은 기록만 한다. 다른 스레드 판단의 잘못은 단언하지 않는다(사용자가 누르기 전에는 합치지 않는 제안이므로).

## 실행 1 → 2 사이에 고친 것

통과 기준은 이미 맞았지만, 판단 잘못은 사용자에게 엉뚱한 "합칠까요?" 제안으로 보이므로 판단 규칙 한 줄을 더했다(설계 11절 "측정 결과에 따라 프롬프트를 고친다").

- `app/mail/intake.py` `INTAKE_SYSTEM`: 메일이 "기존 건과 별개", "별건으로"처럼 다른 건이라고 밝히거나 후보와 다른 품목 · 다른 일을 새로 요청하면, 후보를 언급하더라도 `relation="none"`.
- `app/mail/related.py` `candidates_block`: 같은 내용을 후보 블록 안내에도 넣었다.

## 사례별로 본 것

- **질문형 · 부드러운 제안:** "11월 13일로 미뤄 주실 수 있을까요?", "목요일쯤 받아 볼 수 있으면 좋겠습니다"는 두 번 모두 `question`으로만 기록되고 기한은 그대로였다.
- **질문 + 확정 섞임:** 납품 장소 변경은 반영, "결제 조건을 60일로 바꿀 수 있을까요?"는 질문으로 분리했다.
- **사용자가 정한 기한:** 상대가 "11월 17일로 확정합니다"라고 해도 덮지 않고 제안(`suggested`)으로 남았다.
- **인용된 옛 내용 · 감사 인사 · 본문 주입:** 변경 0건, 답장 필요 false, 감사 인사는 "답장 필요 없음" 표시가 붙었다.
  (측정은 LLM + 코드 거르기 전체 결과다. 인용 문장을 LLM이 냈다가 코드가 버렸는지는 따로 세지 않았다.)
- **초안:** 메모 · 입력에 없는 납기 · 단가 · 최소 수량은 모두 `[[납기 일정 입력]]` 같은 빈칸으로 남았다. 주입 사례는 지시를
  따르지 않았고(원가 자료 · 다른 연락처 · 외부 참조 주소 없음) suspicious에 1건 기록했다.

## 남은 놓침 · 사용자에게 뜻하는 것

- 최종 실행의 놓침은 0건이다. 다만 사례가 25건뿐이고 문장이 비교적 또렷하다. 실제 메일은 더 애매하므로 놓침은 생길 수 있다.
  놓치면 그 변경은 업무 카드에 반영되지 않고(사용자가 메일을 직접 보고 고친다), 다른 스레드 수정 요청은 별도 업무로 남는다. 데이터가 망가지지는 않는다.
- 실행 1의 판단 잘못처럼, 모델이 바뀌거나 문장이 달라지면 "언급만 한 별건"에 합치기를 제안할 수 있다. 제안은 사용자가 눌러야 합쳐지고 되돌릴 수 있다.
- 초안 본문이 한 문단으로 나오는 경우가 많았다(줄바꿈 없이). 사실 오류는 아니지만 읽기가 불편할 수 있어 나중에 서식 규칙을 검토할 만하다.
- 근거 없는 숫자 검사는 토큰 비교라서, 초안이 "14:00"처럼 입력("오후 2시")과 다른 표기로 쓰면 경고가 날 수 있다(이번 측정에서는 나오지 않았다).
- 같은 사례라도 실행마다 결과가 조금씩 다르다(LLM 비결정성). 2회 실행으로 본 결과다.
