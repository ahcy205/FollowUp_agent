# 문제 해결 모음

실제로 겪었거나 겪기 쉬운 문제와 해결법을 모았습니다. 새로 겪은 문제는 같은 형식으로 추가해 주세요.

**서버 로그 보는 법:** 백엔드를 띄운 터미널 출력을 봅니다. 로그에는 메일 내용이 남지 않으므로 공유해도 안전합니다. 다만 URL 속 `code=`, `state=` 값은 지우고 공유하세요.

## Google 연결

### "Google 응답 처리 중 오류가 났습니다"가 뜬다
- **증상:** 연결 후 설정 화면에 위 문구가 뜬다. 서버 로그에는 `POST https://oauth2.googleapis.com/token "401 Unauthorized"`와 `google code exchange failed ... GoogleAuthError`가 찍힌다.
- **원인:** `GOOGLE_CLIENT_SECRET`이 `GOOGLE_CLIENT_ID`와 짝이 맞지 않는다. 클라이언트를 여러 개 만들었거나, 비밀번호를 새로 발급해 예전 값이 무효가 된 경우다.
- **해결:**
  1. Google Cloud Console → Google 인증 플랫폼 → 클라이언트에서 ID가 같은 클라이언트를 엽니다.
  2. **보안 비밀번호 추가**로 새 비밀번호를 만들어 `.env`에 넣습니다.
  3. 서버를 재시작합니다.

### "redirect_uri_mismatch" 오류 화면이 Google에서 뜬다
- **원인:** Google 클라이언트에 등록한 리디렉션 URI와 `.env`의 `PUBLIC_URL`이 맞지 않는다.
- **해결:** 등록 URI는 정확히 `{PUBLIC_URL}/api/google/callback`이어야 합니다. 예: `http://localhost:8000/api/google/callback`. 끝의 `/`, `http`와 `https`, 포트 번호까지 같아야 합니다.

### 연결 후 로그인 화면으로 돌아가거나 "연결 요청이 만료되었거나 올바르지 않습니다"
- **원인:** 앱을 `127.0.0.1`로 열었는데 Google은 `localhost`로 돌려보냈다. 두 주소는 로그인 쿠키가 따로라서 세션이 끊긴다.
- **해결:** 앱을 항상 `PUBLIC_URL`과 같은 주소(`http://localhost:8000`)로 엽니다.

### Google 화면에 "Google에서 확인하지 않은 앱입니다" 경고
- **원인:** 본인이 만든 테스트 상태 앱이라 정상이다.
- **해결:** **고급** → **FollowUp Agent(으)로 이동(안전하지 않음)**을 누릅니다.

### "필요한 권한(메일 읽기 · 발송 · 캘린더)이 빠졌습니다"
- **원인:** 동의 화면에서 권한 체크박스를 일부 해제했다.
- **해결:** 다시 연결하면서 모든 항목을 체크합니다.

### "Google에서 장기 토큰을 받지 못했습니다"
- **원인:** 예전 동의 기록이 남아 있어 Google이 갱신 토큰을 다시 주지 않았다.
- **해결:** [Google 계정 → 타사 연결](https://myaccount.google.com/connections)에서 이 앱을 삭제한 뒤 다시 연결합니다.

### 일주일쯤 지나면 상단에 빨간 "Google 연결이 만료되었습니다" 배너
- **원인:** Google 정책상 "테스트" 상태 앱의 갱신 토큰은 7일 뒤 만료된다.
- **해결:** 배너의 **다시 연결**을 누릅니다. 앱을 "프로덕션" 상태로 바꾸면 사라지지만 Google 심사가 필요할 수 있습니다.

## 메일 동기화 · 판별

### 메일을 보냈는데 앱에 안 보인다
- 서버는 90초마다, 설정 화면은 30초마다 갱신한다. **최대 2분**쯤 기다리거나 **지금 확인**을 누릅니다.
- **본인 Gmail에서 본인에게 보낸 메일**은 '보낸 메일'로 분류되어 일부러 저장하지 않습니다. 다른 계정에서 보내야 합니다.
- 받은편지함이 아니라 프로모션 · 스팸으로 간 메일은 가져오지 않거나 자동 필터됩니다.

### 메일이 계속 "판별 대기"에 머문다
- **스위치:** `.env`에 `MAIL_TRIAGE_ENABLED=true`가 있는지, 서버를 재시작했는지 확인합니다. 설정 화면에 "자동 판별이 꺼져 있습니다" 안내가 보이면 꺼진 상태입니다.
- **LLM 키:** `LLM_API_KEY`가 비어 있거나 잘못됐으면 판별을 건너뜁니다.
- **LLM 장애 · 한도:** Gemini가 한도나 장애를 내면 일부러 "판별 대기"로 두고 다음 주기에 다시 시도합니다. 잠시 기다리면 됩니다.

### "자동 판별에 실패했습니다 — 직접 확인해 주세요"
- **원인:** LLM이 형식에 맞지 않는 응답을 3번 줬다.
- **해결:** 메일을 직접 확인합니다. "업무로 처리" 버튼은 5단계에서 추가됩니다.

### Gemini가 느리거나 429 오류
- **원인:** 무료 등급은 분당 호출 수가 적다(약 5회). 앱은 `LLM_RPM_LIMIT`로 호출 속도를 스스로 조절한다.
- **해결:** 메일이 많으면 판별과 분석이 여러 주기에 나눠 처리됩니다. 빠르게 하려면 유료 등급 키를 쓰고 `LLM_RPM_LIMIT`을 올립니다.

## 캘린더

### 기한이 있는 업무인데 캘린더에 일정이 안 생긴다
- 일정은 메일 동기화와 같은 주기(90초)에 만들어집니다. "지금 확인" 버튼으로는 만들어지지 않으니 잠시 기다립니다.
- 업무 상세에 빨간 오류와 **다시 시도** 버튼이 보이면 눌러 봅니다.
- 이미 완료 · 취소된 업무는 일정이 없으면 새로 만들지 않습니다(의도된 동작).
- "같은 번호의 다른 캘린더 일정이 있어 반영하지 못했습니다": 다른 데이터베이스나 다른 서버가 같은 번호로 만든 일정이 있다는 뜻입니다. 남의 일정을 덮어쓰지 않으려고 멈춘 것입니다.

### 캘린더에서 일정을 지웠는데 업무 상세에는 "캘린더에 등록됨"으로 나온다
- **원인:** 앱은 캘린더를 주기적으로 확인하지 않는다. 다음에 그 일정을 고치려 할 때 삭제를 알아차린다(업무 취소, 기한 변경 등).
- **해결:** 그때 "캘린더에서 삭제된 일정입니다"로 바뀌고, 다시 만들지 않습니다. 따로 할 일은 없습니다.

### 일정 내용을 다른 사람이 볼까 걱정된다
- 앱이 만드는 일정은 비공개입니다. 캘린더를 공유해도 상대에게는 "바쁨"으로만 보입니다. 자세한 내용은 [데이터 · 개인정보 흐름](privacy.md)에 있습니다.

## 서버 · DB

### 코드를 받은 뒤 서버에서 "no such column" 같은 DB 오류
- **원인:** 새 코드에 DB 컬럼이 추가됐는데 로컬 DB에 반영되지 않았다. 로컬 SQLite는 새 테이블만 자동으로 만들고, 기존 테이블에 컬럼을 추가하지 않는다.
- **해결:**
  ```bash
  cd backend
  cp dev.db dev.db.bak-$(date +%Y%m%d)        # 백업 (git에는 올라가지 않음). 서버가 떠 있으면 아래 항목처럼 백업
  ../.venv/Scripts/python -m alembic upgrade head
  ```

### 서버가 떠 있을 때 `cp dev.db`로 만든 백업이 최신이 아니다
- **원인:** SQLite가 WAL 모드로 동작하면 최근 변경이 `dev.db-wal`에 먼저 쌓이고, 나중에 `dev.db`로 옮겨진다. 서버가 떠 있는 동안 `dev.db`만 복사하면 최근 변경이 빠진 복사본이 생긴다(`dev.db-wal`·`dev.db-shm`을 따로 복사해도 순간이 어긋날 수 있다).
- **해결:** 서버를 먼저 끄고 복사하거나, SQLite 백업 기능으로 복사합니다. 백업 기능은 서버가 떠 있어도 일관된 복사본을 만든다.
  ```bash
  cd backend
  sqlite3 dev.db ".backup dev.db.bak-YYYYMMDD"
  # sqlite3 명령이 없으면 Python으로
  ../.venv/Scripts/python -c "import sqlite3; s=sqlite3.connect('dev.db'); d=sqlite3.connect('dev.db.bak-YYYYMMDD'); s.backup(d); d.close(); s.close()"
  ```

### 서버를 띄우면 "address already in use" / 8000 포트 사용 중
- **원인:** 이전 서버가 아직 떠 있다.
- **해결 (Windows):** `netstat -ano | findstr :8000`으로 PID를 찾아 `taskkill /PID <번호> /F`로 종료합니다.

### `.env`를 고쳤는데 반영이 안 된다
- **원인:** 설정은 서버가 시작할 때 한 번만 읽는다.
- **해결:** 서버를 재시작합니다.

### 서버가 갑자기 종료됐다
- **해결:** 서버를 띄운 터미널의 마지막 출력을 확인합니다. 로그를 파일로 남기고 있다면 그 파일이 지워지지 않았는지 확인합니다. 원인을 찾으면 이 문서에 추가해 주세요.

## 테스트 · 개발

### 테스트가 내 PC에서만 실패한다 (예: "Google 미설정"을 가정한 테스트)
- **원인:** 테스트가 실제 `backend/.env` 값을 읽었다.
- **해결:** 테스트는 `backend/tests/conftest.py` 맨 위에서 환경변수를 고정합니다. **새 설정을 추가하면 테스트가 기대하는 값을 여기에도 고정**하세요.

### 스모크 테스트를 `-s`로 돌리면 `UnicodeEncodeError` (Windows)
- **원인:** Windows 콘솔의 기본 인코딩(cp949)이 일부 문자(`—` 등)를 못 쓴다.
- **해결:** `PYTHONUTF8=1`을 붙입니다.
  ```bash
  cd backend && PYTHONUTF8=1 RUN_LLM_SMOKE=1 ../.venv/Scripts/python -m pytest smoke -v -s
  ```

### Claude Code가 브랜치 삭제를 "Git Destructive"로 막는다
- **원인:** auto 모드의 안전장치다.
- **해결:** 병합된 로컬 브랜치 삭제(`git branch -d`)는 `.claude/settings.local.json`에 허용해 두었습니다. 원격 브랜치 삭제는 매번 직접 확인합니다.

### CI가 실패한다
- GitHub 저장소 → **Actions** 탭에서 실패한 단계(backend / frontend)의 로그를 봅니다.
- CI는 `.env` 없이 깨끗한 환경에서 돌기 때문에, 내 PC 설정에 기대던 문제가 여기서 드러납니다.
