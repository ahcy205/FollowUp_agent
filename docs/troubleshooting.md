# 문제 해결 모음

실제로 겪었거나 겪기 쉬운 문제와 해결법을 모았습니다. 새로 겪은 문제는 같은 형식으로 추가해 주세요.

**서버 로그 보는 법:** 백엔드를 띄운 터미널 출력을 봅니다. 로그에는 메일 내용이 남지 않으므로 공유해도 안전합니다. 다만 URL 속 `code=`, `state=` 값은 지우고 공유하세요.

---

## Google 연결

### "Google 응답 처리 중 오류가 났습니다"가 뜬다
- **증상:** 연결 후 설정 화면에 위 문구가 뜬다. 서버 로그에는 `POST https://oauth2.googleapis.com/token "401 Unauthorized"`와 `google code exchange failed ... GoogleAuthError`가 찍힌다.
- **원인:** `GOOGLE_CLIENT_SECRET`이 `GOOGLE_CLIENT_ID`와 짝이 맞지 않는다. 클라이언트를 여러 개 만들었거나, 비밀번호를 새로 발급해 예전 값이 무효가 된 경우다.
- **해결:**
  1. Google Cloud Console → Google 인증 플랫폼 → 클라이언트에서 ID가 같은 클라이언트를 엽니다.
  2. **보안 비밀번호 추가**로 새 비밀번호를 만들어 `.env`에 넣습니다.
  3. 서버를 재시작합니다.

### "redirect_uri_mismatch" 오류 화면이 Google에서 뜬다
- **원인:** Google 클라이언트에 등록한 리디렉션 URI와 `.env`의 `PUBLIC_URL`이 맞지 않는다.
- **해결:** 등록 URI는 정확히 `{PUBLIC_URL}/api/google/callback`이어야 합니다. 예: `http://localhost:8000/api/google/callback`. 끝의 `/`, `http`와 `https`, 포트 번호까지 같아야 합니다.

### 연결 후 로그인 화면으로 돌아가거나 "연결 요청이 만료되었거나 올바르지 않습니다"
- **원인:** 앱을 `127.0.0.1`로 열었는데 Google은 `localhost`로 돌려보냈다. 두 주소는 로그인 쿠키가 따로라서 세션이 끊긴다.
- **해결:** 앱을 항상 `PUBLIC_URL`과 같은 주소(`http://localhost:8000`)로 엽니다.

### Google 화면에 "Google에서 확인하지 않은 앱입니다" 경고
- **원인:** 본인이 만든 테스트 상태 앱이라 정상이다.
- **해결:** **고급** → **FollowUp Agent(으)로 이동(안전하지 않음)**을 누릅니다.

### "필요한 권한(메일 읽기 · 발송 · 캘린더)이 빠졌습니다"
- **원인:** 동의 화면에서 권한 체크박스를 일부 해제했다.
- **해결:** 다시 연결하면서 모든 항목을 체크합니다.

### "Google에서 장기 토큰을 받지 못했습니다"
- **원인:** 예전 동의 기록이 남아 있어 Google이 갱신 토큰을 다시 주지 않았다.
- **해결:** [Google 계정 → 타사 연결](https://myaccount.google.com/connections)에서 이 앱을 삭제한 뒤 다시 연결합니다.

### 일주일쯤 지나면 상단에 빨간 "Google 연결이 만료되었습니다" 배너
- **원인:** Google 정책상 "테스트" 상태 앱의 갱신 토큰은 7일 뒤 만료된다.
- **해결:** 배너의 **다시 연결**을 누릅니다. 앱을 "프로덕션" 상태로 바꾸면 사라지지만 Google 심사가 필요할 수 있습니다.

## 메일 동기화 · 판별

### 메일을 보냈는데 앱에 안 보인다
- 서버는 90초마다, 설정 화면은 30초마다 갱신한다. **최대 2분**쯤 기다리거나 **지금 확인**을 누릅니다.
- **본인 Gmail에서 본인에게 보낸 메일**은 '보낸 메일'로 분류되어 일부러 저장하지 않습니다. 다른 계정에서 보내야 합니다.
- 받은편지함이 아니라 프로모션 · 스팸으로 간 메일은 가져오지 않거나 자동 필터됩니다.

### 메일이 계속 "판별 대기"에 머문다
- **스위치:** `.env`에 `MAIL_TRIAGE_ENABLED=true`가 있는지, 서버를 재시작했는지 확인합니다. 설정 화면에 "자동 판별이 꺼져 있습니다" 안내가 보이면 꺼진 상태입니다.
- **LLM 키:** `LLM_API_KEY`가 비어 있거나 잘못됐으면 판별을 건너뜁니다.
- **LLM 장애 · 한도:** Gemini가 한도나 장애를 내면 일부러 "판별 대기"로 두고 다음 주기에 다시 시도합니다. 잠시 기다리면 됩니다.

### "자동 판별에 실패했습니다 — 직접 확인해 주세요"
- **원인:** LLM이 형식에 맞지 않는 응답을 3번 줬다.
- **해결:** 메일을 직접 확인합니다. "업무로 처리" 버튼은 5단계에서 추가됩니다.

### Gemini가 느리거나 429 오류
- **원인:** 무료 등급은 분당 호출 수가 적다(약 5회). 앱은 `LLM_RPM_LIMIT`로 호출 속도를 스스로 조절한다.
- **해결:** 메일이 많으면 판별과 분석이 여러 주기에 나눠 처리됩니다. 빠르게 하려면 유료 등급 키를 쓰고 `LLM_RPM_LIMIT`을 올립니다.

## 캘린더

### 기한이 있는 업무인데 캘린더에 일정이 안 생긴다
- 일정은 메일 동기화와 같은 주기(90초)에 만들어집니다. "지금 확인" 버튼으로는 만들어지지 않으니 잠시 기다립니다.
- 업무 상세에 빨간 오류와 **다시 시도** 버튼이 보이면 눌러 봅니다.
- 이미 완료 · 취소된 업무는 일정이 없으면 새로 만들지 않습니다(의도된 동작).
- "같은 번호의 다른 캘린더 일정이 있어 반영하지 못했습니다": 다른 데이터베이스나 다른 서버가 같은 번호로 만든 일정이 있다는 뜻입니다. 남의 일정을 덮어쓰지 않으려고 멈춘 것입니다.

### 캘린더에서 일정을 지웠는데 업무 상세에는 "캘린더에 등록됨"으로 나온다
- **원인:** 앱은 캘린더를 주기적으로 확인하지 않는다. 다음에 그 일정을 고치려 할 때 삭제를 알아차린다(업무 취소, 기한 변경 등).
- **해결:** 그때 "캘린더에서 삭제된 일정입니다"로 바뀌고, 다시 만들지 않습니다. 따로 할 일은 없습니다.

### 일정 내용을 다른 사람이 볼까 걱정된다
- 앱이 만드는 일정은 비공개입니다. 캘린더를 공유해도 상대에게는 "바쁨"으로만 보입니다. 자세한 내용은 [데이터 · 개인정보 흐름](privacy.md)에 있습니다.

## 받은 업무 · 알림

### 브라우저 알림이 안 뜬다
- 설정 → "브라우저 알림"에서 **알림 허용**을 누르고, 브라우저 창에서도 허용했는지 본다. 주소창 왼쪽 자물쇠 → 알림이 "차단"이면 "허용"으로 바꾼다.
- 알림은 **앱 탭이 열려 있을 때만** 1분 간격으로 확인한다. 탭을 닫으면 오지 않는다.
- 대상은 "처리할 일" 탭 업무뿐이다. 기한 하루 전 · 당일(오전 9시 이후), 나중에 보기 해제, 답장 이틀째 미처리.
- 같은 알림은 한 번만 뜬다(브라우저 저장소에 기록). 다시 보고 싶으면 개발자 도구 → Application → Local Storage에서 `followup.shownAlerts` 항목을 지운다.
- Windows "집중 지원(방해 금지)"이 켜져 있으면 알림이 알림 센터에만 쌓인다.

### "나중에 보기" 버튼이 없다
- "처리할 일" 탭의 업무에만 있다. 참고용 · 끝난 업무에는 나오지 않는다.

### 업무 상세에 "캘린더 반영 대기 중"이 계속 보인다
- 보통 몇 초 안에 바뀐다. 1분 넘게 그대로면 서버 로그에서 `calendar sync` 줄의 `errors` 수를 보고, 업무 상세의 "다시 시도"를 누른다.
- Google에 연결하지 않은 계정은 반영할 캘린더가 없어 대기 상태로 남는다.

## 답장

### "답장 초안 만들기"를 누르면 "자동 판별이 꺼져 있어 초안을 만들 수 없습니다."
- **원인:** 초안은 실제 메일을 LLM에 보내므로 `MAIL_TRIAGE_ENABLED`가 켜져 있을 때만 만든다.
- **해결:** `.env`에 `MAIL_TRIAGE_ENABLED=true`를 넣고 서버를 재시작합니다. 켜기 전에 [데이터 · 개인정보 흐름](privacy.md)의 LLM 전송 범위를 확인하세요. 끄고 쓰려면 Gmail에서 직접 답장합니다(보낸 답장은 감지됩니다).
- 같은 자리에 뜰 수 있는 다른 문구:
  - "받은 메일이 없어 답장할 상대를 정할 수 없습니다." / "답장할 상대를 찾지 못했습니다.": 이 업무의 받은 메일이 모두 내 주소에서 온 경우입니다. Gmail에서 직접 답장합니다.
  - "초안을 만들지 못했습니다. 다시 시도해 주세요.": LLM이 형식에 맞지 않는 응답을 두 번 줬습니다. 다시 누릅니다.
  - "AI 응답이 지연되고 있습니다. 잠시 후 다시 시도해 주세요.": LLM 한도 · 장애입니다. 잠시 뒤 다시 누릅니다.
  - "초안을 보내는 중이거나 발송 여부를 확인하는 중이라 바꿀 수 없습니다. 잠시 후 다시 확인해 주세요.": 아래 "발송 여부를 확인하는 중" 항목을 봅니다.
- 닫혔거나 다른 업무에 합쳐진 업무에는 버튼이 없습니다.

### "빈칸 N개를 채워야 보낼 수 있습니다"
- **원인:** 초안 본문에 `[[납기 일정 입력]]` 같은 빈칸이 남아 있다. 상대가 물었는데 할 일 메모나 "답장에 넣을 내용"에 답이 없는 항목이다.
- **해결:** 본문에서 `[[ … ]]`를 실제 내용으로 바꾸거나 지웁니다. 본문 아래 "남은 빈칸" 목록에서 무엇이 남았는지 볼 수 있습니다. 같은 내용을 할 일 메모에 적고 **다시 만들기**를 눌러도 됩니다.
- 화면을 거치지 않고 보내면 서버가 "채우지 않은 빈칸 [[ ]]이 N개 있습니다. 빈칸을 채운 뒤 보내 주세요."로 막습니다.
- `[[`만 남은 깨진 표기는 빈칸으로 보지 않습니다.

### 보내기를 눌렀더니 오류가 뜨고 초안이 그대로 있다
초안은 지워지지 않으니 이유를 해결하고 다시 보내면 됩니다. 이 경우들은 메일이 나가지 않은 것이 확실합니다.
- "Google 인증이 만료되어 보내지 못했습니다. Google 연결을 다시 해 주세요." / "Google이 연결되어 있지 않습니다. Google 연결을 다시 해 주세요.": 설정 화면이나 상단 빨간 배너에서 **다시 연결**합니다(테스트 상태 앱은 7일마다 만료, [Google 연결](#일주일쯤-지나면-상단에-빨간-google-연결이-만료되었습니다-배너) 참고).
- "Google에 연결하지 못해 보내지 않았습니다. 잠시 후 다시 보내 주세요.": 토큰 갱신이 일시적으로 실패했습니다.
- "Gmail이 메일을 보내지 않았습니다. 초안은 그대로 있으니 잠시 후 다시 보내 주세요.": Gmail이 요청을 거절했습니다. 반복되면 서버 로그의 예외 이름을 확인합니다.
- "받는 사람이 바뀌었습니다. 초안을 다시 만들어 주세요." / "참조 후보가 바뀌었습니다. 초안을 다시 만들어 주세요.": 초안을 만든 뒤 새 메일이 와서 답할 사람이 달라졌습니다. **다시 만들기**를 누릅니다.
- 분당 5번까지만 보낼 수 있습니다. 넘으면 잠시 뒤 다시 누릅니다.

### "발송 여부를 확인하는 중입니다"가 계속 보인다
- **원인:** 보내는 도중 시간 초과 같은 오류가 나서 메일이 나갔는지 알 수 없다. 두 번 발송을 막으려고 일부러 다시 보내지 못하게 둔 상태다. 서버가 "보내는 중입니다…" 상태에서 멈췄을 때도 5분 뒤 같은 상태가 된다.
- **해결:**
  1. 기다립니다. 동기화(90초마다)가 이 스레드의 보낸 메일을 찾으면(제목 · 받는 사람 · 보낸 시각으로 맞춰 봄) 자동으로 "보냄"으로 바뀝니다.
  2. 5분이 지나면 "Gmail 보낸편지함을 확인해 주세요"와 버튼이 나옵니다. Gmail 보낸편지함을 열어 보고 **[보내진 걸 확인했어요]** 또는 **[안 보내졌어요]**를 누릅니다. 안 보내졌으면 초안으로 돌아가 다시 보낼 수 있습니다.
- 5분 전에 확인 요청을 보내면 "아직 발송 여부를 확인하는 중입니다. 잠시 후 다시 확인해 주세요."가 뜹니다.
- **[안 보내졌어요]**를 눌렀는데 "Gmail에서 이 답장이 이미 보내진 것으로 확인됩니다. 보낸편지함을 확인해 주세요.": 동기화가 이미 보낸 답장을 찾았습니다. 보낸편지함을 다시 확인합니다. 두 번 보내지 않으려고 막은 것입니다.
- 이 상태에서는 초안 고치기 · 다시 만들기, 그 업무 합치기도 막힙니다.

### 보내기를 누르면 "이미 답장을 보낸 것으로 확인됐습니다. 초안을 지우거나 다시 만들어 주세요."
- **원인:** 이 초안을 만든(또는 고친 · 초안으로 되돌린) 뒤에 이 업무에서 보낸 답장이 확인됐다. Gmail에서 직접 답장했거나, **[안 보내졌어요]**를 누른 뒤 동기화가 실제로 나간 답장을 찾은 경우다.
- **해결:** Gmail 보낸편지함에서 답장이 나갔는지 봅니다. 나갔으면 **초안 지우기**를 누릅니다. 정말 한 번 더 보내야 하면 **다시 만들기**로 새 초안을 만듭니다.

### Gmail에서 직접 보낸 답장이 감지되지 않는다 ("답장 보냄"으로 안 바뀜)
- **기다리기:** 동기화는 90초마다 돈다. 최대 2분쯤 기다리거나 설정의 **지금 확인**을 누릅니다.
- **같은 대화(스레드)에서 답장했는지:** 앱은 업무가 있거나 받은 메일이 저장된 스레드의 보낸 메일만 저장합니다. Gmail에서 **새 메일 작성**으로 보냈거나 제목을 바꿔 다른 대화가 됐으면 감지하지 않습니다. 이때는 업무를 직접 닫거나 그대로 둡니다.
- **아주 드문 경우:** 메일이 한꺼번에 많이 들어와 받은 메일과 보낸 메일이 서로 다른 동기화 묶음으로 나뉘면, 앱이 그 스레드를 아직 몰라 보낸 메일을 건너뛸 수 있습니다. 이미 지나간 보낸 메일은 다시 가져오지 않습니다. 업무를 직접 처리합니다.
- **동료에게 전달(Fwd)한 것도 답장으로 셉니다.** 업무 스레드에서 보낸 메일은 받는 사람과 상관없이 "답장 보냄"으로 옮겨집니다(알려진 한계).

### 합치기를 누르면 "합친 내용을 분석하는 중입니다. 잠시 후 다시 합쳐 주세요."
- **원인:** 원본이나 대상 업무에 방금 합친 내용을 분석하는 작업이 아직 끝나지 않았다. 분석이 섞이지 않게 업무마다 하나씩만 한다.
- **해결:** 업무 상세의 "합친 내용을 분석하는 중입니다" 표시가 사라질 때까지(보통 다음 동기화, LLM 한도가 걸리면 몇 분) 기다렸다가 다시 합칩니다. 10분 넘게 끝나지 않으면 앱이 5단계 규칙(요청 합치기 · 이른 기한)으로 마무리합니다.
- 비슷한 문구 "보내는 중인 답장이 있어 합칠 수 없습니다. 발송 결과를 확인한 뒤 다시 시도해 주세요.": 두 업무 중 하나에 발송 결과를 확인하는 초안이 있습니다. 위 "발송 여부를 확인하는 중" 항목대로 먼저 정리합니다.

### "상대 답장으로 바뀐 내용"의 [되돌리기]가 "그 뒤에 직접 고친 내용이 있어 되돌릴 수 없습니다."
- **원인:** 그 변경 뒤에 같은 항목(기한, 요청, 할 일 등)을 직접 고쳤거나, 추가된 할 일을 체크했다. 사용자가 고친 값을 덮지 않으려고 막는다.
- **해결:** 원하는 값으로 직접 고칩니다.

### "보낸 지 영업일 3일째 답이 없습니다"가 예상과 다른 날 뜬다
- 영업일은 월~금만 세고 **공휴일은 빼지 않는다.** 명절 · 공휴일이 끼면 일찍 뜬다.
- 금요일 오후에 보내면 다음 주 수요일 같은 시각, 주말에 보내면 그다음 목요일 0시에 뜬다(사용자 시간대 `USER_TIMEZONE` 기준).
- Gmail에서 보낸 답장은 메일을 보낸 시각부터 센다. 서버가 꺼져 있던 동안 보낸 답장도 마찬가지다.
- **[더 기다리기]**를 누르면 그때부터 영업일 3일을 다시 센다.

## 서버 · DB

### 코드를 받은 뒤 서버에서 "no such column" 같은 DB 오류
- **원인:** 새 코드에 DB 컬럼이 추가됐는데 로컬 DB에 반영되지 않았다. 로컬 SQLite는 새 테이블만 자동으로 만들고, 기존 테이블에 컬럼을 추가하지 않는다.
- **해결:**
  ```bash
  cd backend
  cp dev.db dev.db.bak-$(date +%Y%m%d)        # 백업 (git에는 올라가지 않음). 서버가 떠 있으면 아래 항목처럼 백업
  ../.venv/Scripts/python -m alembic upgrade head
  ```

### 서버가 떠 있을 때 `cp dev.db`로 만든 백업이 최신이 아니다
- **원인:** SQLite가 WAL 모드로 동작하면 최근 변경이 `dev.db-wal`에 먼저 쌓이고, 나중에 `dev.db`로 옮겨진다. 서버가 떠 있는 동안 `dev.db`만 복사하면 최근 변경이 빠진 복사본이 생긴다(`dev.db-wal`·`dev.db-shm`을 따로 복사해도 순간이 어긋날 수 있다).
- **해결:** 서버를 먼저 끄고 복사하거나, SQLite 백업 기능으로 복사합니다. 백업 기능은 서버가 떠 있어도 일관된 복사본을 만든다.
  ```bash
  cd backend
  sqlite3 dev.db ".backup dev.db.bak-YYYYMMDD"
  # sqlite3 명령이 없으면 Python으로
  ../.venv/Scripts/python -c "import sqlite3; s=sqlite3.connect('dev.db'); d=sqlite3.connect('dev.db.bak-YYYYMMDD'); s.backup(d); d.close(); s.close()"
  ```

### 서버를 띄우면 "address already in use" / 8000 포트 사용 중
- **원인:** 이전 서버가 아직 떠 있다.
- **해결 (Windows):** `netstat -ano | findstr :8000`으로 PID를 찾아 `taskkill /PID <번호> /F`로 종료합니다.

### `.env`를 고쳤는데 반영이 안 된다
- **원인:** 설정은 서버가 시작할 때 한 번만 읽는다.
- **해결:** 서버를 재시작합니다.

### 서버가 갑자기 종료됐다
- **해결:** 서버를 띄운 터미널의 마지막 출력을 확인합니다. 로그를 파일로 남기고 있다면 그 파일이 지워지지 않았는지 확인합니다. 원인을 찾으면 이 문서에 추가해 주세요.

## 테스트 · 개발

### 테스트가 내 PC에서만 실패한다 (예: "Google 미설정"을 가정한 테스트)
- **원인:** 테스트가 실제 `backend/.env` 값을 읽었다.
- **해결:** 테스트는 `backend/tests/conftest.py` 맨 위에서 환경변수를 고정합니다. **새 설정을 추가하면 테스트가 기대하는 값을 여기에도 고정**하세요.

### 스모크 테스트를 `-s`로 돌리면 `UnicodeEncodeError` (Windows)
- **원인:** Windows 콘솔의 기본 인코딩(cp949)이 일부 문자(`—` 등)를 못 쓴다.
- **해결:** `PYTHONUTF8=1`을 붙입니다.
  ```bash
  cd backend && PYTHONUTF8=1 RUN_LLM_SMOKE=1 ../.venv/Scripts/python -m pytest smoke -v -s
  ```

### Claude Code가 브랜치 삭제를 "Git Destructive"로 막는다
- **원인:** auto 모드의 안전장치다.
- **해결:** 병합된 로컬 브랜치 삭제(`git branch -d`)는 `.claude/settings.local.json`에 허용해 두었습니다. 원격 브랜치 삭제는 매번 직접 확인합니다.

### CI가 실패한다
- GitHub 저장소 → **Actions** 탭에서 실패한 단계(backend / frontend)의 로그를 봅니다.
- CI는 `.env` 없이 깨끗한 환경에서 돌기 때문에, 내 PC 설정에 기대던 문제가 여기서 드러납니다.
