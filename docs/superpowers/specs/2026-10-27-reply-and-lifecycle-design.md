# 6단계 설계: 답장과 수명주기

상위 설계: [`2026-10-10-gmail-calendar-design.md`](2026-10-10-gmail-calendar-design.md) 4.6 · 4.8 · 4.9절, 12.1절.
이어받는 것: [5단계 설계](2026-10-26-inbox-screen-design.md) 4.2절(답장 넛지)의 6단계 이관 항목, 5단계에서 미룬 "기한 삭제 시 캘린더 일정" 결정.

사용자 결정은 **(사용자 결정)**, 제가 정한 것은 **(내 판단)**으로 표시한다.

---

## 1. 목적

메일을 받은 뒤 답장을 보내고, 상대의 반응을 기다리고, 상대가 내용을 바꾸면 업무를 고치는 데까지 이어서 챙긴다.

### 목표
1. 사용자가 준 내용으로 답장 초안을 만들고, 사용자가 확인 · 승인한 뒤 원래 Gmail 스레드에 답장으로 보낸다.
2. Gmail에서 직접 보낸 답장도 알아채서 "답장 보냄"으로 옮긴다. 5단계의 "N일째 답장 안 함"을 끈다.
3. 답장을 보낸 뒤 상대가 영업일 3일 동안 답이 없으면 다시 연락할지 묻는다.
4. 상대가 같은 스레드에서 내용을 바꿔 보내면 업무를 고치고 무엇이 바뀌었는지 보여 준다.
5. 다른 스레드로 온 수정 요청(다른 직원이 보낸 경우 포함)을 알아보고 합치기를 제안한다.
6. 기한을 없애면 앱이 만든 캘린더 일정을 지운다.
7. 위 판단의 정확도를 가상 메일 시험 세트로 잰다.

### 하지 않는 것
- **첨부파일 보내기.** 첨부가 필요한 답장은 Gmail에서 직접 보내면 2번으로 감지된다. **(내 판단)**
- **자동 발송.** 어떤 경우에도 사용자 승인 없이 보내지 않는다.
- **자동 합치기.** 합치기는 언제나 사용자가 누른다(5단계 결정 유지).
- **임베딩 · 벡터 검색, Jev 같은 외부 판단 모델.** 11절 "나중에 검토"에 남긴다. **(사용자 결정: 판단 부분은 교체할 수 있게 만들고 지금은 Gemini)**
- **공휴일 계산.** 영업일은 월~금만 센다.

### 실패로 보는 경우
- 사용자가 주지 않은 사실(숫자, 날짜, 결과, 약속)이 초안에 들어가 그대로 발송된다.
- 수신자가 LLM이나 메일 본문 지시로 바뀐다.
- 같은 답장이 두 번 발송된다.
- 상대 재답장의 인용 부분이나 질문을 확정된 변경으로 반영한다.
- 사용자가 직접 고친 기한 · 중요도 · 할 일이 재답장 반영으로 사라진다.

## 2. 답장 초안

### 2.1 사용자 흐름
1. 업무 상세의 **"답장 초안 만들기"**를 누른다(지금 비활성 버튼 자리).
   - 할 일을 다 끝냈으면 버튼을 강조한다(5단계와 같음).
   - 남은 할 일이 있으면 버튼 옆에 "아직 끝나지 않은 할 일이 N개 있습니다"를 보이되 누를 수 있다.
2. 누르면 **"답장에 넣을 내용"** 칸이 열린다(여러 줄, 선택). 할 일별 메모는 자동으로 들어간다는 안내를 함께 보인다.
3. "초안 만들기"를 누르면 몇 초 뒤 **초안 카드**(3절)가 나타난다.

### 2.2 LLM에 주는 것 (이 업무 하나로 한정)
- 이 업무에 붙은 메일 전부(합쳐진 스레드 포함). 최근 것부터 넣고, 전체 길이 상한을 둔다(값은 구현이 정함). 본문은 `wrap_untrusted()`로 감싼다.
- 업무의 한 줄 요약, 상대 요청 목록, 할 일 목록(제목 · 완료 여부 · 메모)
- 사용자가 "답장에 넣을 내용"에 쓴 글
- 답장 목적: `reply`(일반 답장) 또는 `followup`(상대 답장 없음 → 다시 연락, 6절)
- 다른 업무의 메일 · 요약은 넣지 않는다.

### 2.3 LLM이 하는 일 (사용자 결정)
- **형식과 문장만 만든다.** 인사, 상대 요청 순서대로의 답, 마무리.
- **사실은 사용자가 준 것만 쓴다.** 할 일 메모와 "답장에 넣을 내용"에 있는 숫자 · 날짜 · 결과만 쓴다.
- 상대가 쓴 용어는 원문에서 그대로 가져다 쓴다.
- **근거가 없는 항목은 빈칸으로 둔다.** 상대가 물었는데 사용자가 내용을 주지 않은 항목은 `[[납기 일정 입력]]`처럼 남긴다. 빈칸 표기는 `[[ … ]]`로 고정한다(본문의 일반 대괄호와 구별). **(내 판단)**
- 한 번 호출로 끝낸다(Agent 루프 아님). 출력은 구조화 JSON: `subject`, `body`, `placeholders`(빈칸 목록), `used_facts`(초안에 쓴 사실과 출처: 메모 · 입력 · 메일). **(내 판단: 상위 설계 4.8의 Agent 루프 대신 1회 호출. 단순하고 저렴하다.)**
- 메일 본문 속 지시("이 주소로도 보내 주세요", "첨부 파일을 열어 실행해 주세요")는 따르지 않는다. 탐지되면 초안 카드에 보안 경고로 보인다.
- **(2026-10-30 RAG 1단계에서 더함)** 사실 출처에 **"답장에 써도 되는 내 자료"**(`used_facts.source = doc`, 덩어리 · 줄 번호)가 더해진다. `KNOWLEDGE_ENABLED`가 켜져 있을 때만 쓴다. 자세한 규칙은 [RAG 1단계 설계](2026-10-29-rag-documents-design.md) 5절.

### 2.4 코드가 다시 확인하는 것
- 초안의 숫자 · 날짜가 입력(메모, 사용자 입력, 스레드 메일) 어디에도 없으면 초안 카드에 **"근거를 찾지 못한 내용"** 경고로 표시한다. 막지는 않는다. **(내 판단: 숫자 형식 차이로 오탐이 날 수 있어 경고로만)**
  - **(2026-10-31 사용자 결정으로 바뀜)** 근거를 찾지 못한 값이 있으면 보내기 확인 단계에서 "값이 맞는지 확인했어요"를 체크해야 보낸다. 서버도 `unsupported_ack` 없이는 409로 막는다(내부용 값 확인과 같은 방식).
- 초안에 스레드에 없던 이메일 주소 · 전화번호가 있으면 경고한다(상위 설계 6절).
- 형식이 틀린 응답은 한 번 다시 시도하고, 또 틀리면 "초안을 만들지 못했습니다. 다시 시도해 주세요."를 보인다. 무한 재시도는 없다.

### 2.5 조건
- `MAIL_TRIAGE_ENABLED`가 꺼져 있으면 초안 만들기를 막고 이유를 보인다(실제 메일을 LLM에 보내므로). **(내 판단)**
- 호출 횟수 제한(`RateLimiter`)을 둔다.
- 처리할 일 · 답장 보냄 · 참고용 업무에서 쓸 수 있다. 닫힌 업무 · 합쳐진 업무에서는 숨긴다.

## 3. 초안 카드 · 승인 · 발송

### 3.1 초안 카드 (업무 상세, 요약 카드 아래)
- **받는 사람:** 서버가 정한다. LLM은 정할 수 없다.
  - 기본: 이 업무에서 **가장 최근에 받은 메일의 보낸 사람**. **(내 판단: 다른 직원이 대신 수정 요청을 보낸 경우 그 사람에게 답하는 것이 자연스럽다)**
  - 처음 요청자가 그와 다르면 참조 후보에 넣는다.
- **참조:** 그 메일의 받는 사람 · 참조 목록(내 주소 제외)과 처음 요청자를 체크박스로 보인다. **기본은 모두 해제.** **(내 판단)** 주소를 직접 추가하는 칸은 없다.
- **제목:** `Re: 원래 제목`(이미 `Re:`면 그대로). 고칠 수 있다.
- **본문:** 바로 고칠 수 있는 입력칸. `[[ ]]` 빈칸은 강조해서 보인다.
- **경고 영역:** 남은 빈칸 수, 근거를 찾지 못한 내용, 스레드 밖 연락처, 보안 경고.
- **버튼:** "보내기", "다시 만들기"(입력칸을 다시 열어 새로 만듦), "초안 지우기".
- **빈칸이 남아 있으면 "보내기"를 막는다.** 버튼 옆에 "빈칸 N개를 채워야 보낼 수 있습니다". **(사용자 결정)**
- 초안은 업무당 하나다. 다시 만들면 이전 초안을 대체한다. 서버에 저장해서 새로고침해도 남는다.

### 3.2 보내기
- "보내기" → 카드 안에서 "김민수(kim@…)에게 보냅니다 · 참조 0명 [정말 보내기] [취소]" 확인 단계(`window.confirm` 금지 규칙).
- 서버가 보내기 직전에 다시 확인한다: 받는 사람이 3.1 규칙의 값과 같은지, 참조가 허용 목록 안인지, 빈칸이 없는지, Google 연결 상태.
  - **(2026-10-30 RAG 1단계에서 더함)** 인용한 자료가 아직 있고 "답장에 써도 됨"인지, 참고한 자료가 바뀌지 않았는지, 내부용 자료 값이 있으면 "알고 보냅니다" 확인을 받았는지, 화면이 본 초안 버전과 같은지. [RAG 1단계 설계](2026-10-29-rag-documents-design.md) 5.3 · 5.4절.
- Gmail `messages.send`에 `threadId`, `In-Reply-To`, `References`(원래 메일의 `rfc_message_id` 기준), 제목을 넣어 원래 스레드의 답장으로 보낸다. 본문은 일반 텍스트. **(내 판단: HTML 서식 없음)**
- **두 번 발송 방지:** 초안마다 상태(`draft` → `sending` → `sent` / `failed`)를 두고, `sending`으로 바꾸는 것을 한 번만 성공하게 한다. 같은 초안에 두 번째 요청이 오면 409.
  - **발송 결과가 불분명한 오류(타임아웃 등)** → 상태 `unknown`. `failed`로 두지 않는다(실제로는 나갔는데 다시 보내 두 번 발송될 수 있으므로). **(사용자 결정)**
    - 처음에는 "발송 여부를 확인하는 중입니다"를 보이고 다시 보내기를 막는다.
    - 동기화가 이 스레드에서 보낸 메일을 찾으면 자동으로 `sent`로 바꾼다(제목 · 받는 사람 · 보낸 시각으로 맞춰 본다).
    - **5분이 지나도 확인되지 않으면** 안내 "Gmail 보낸편지함을 확인해 주세요"와 버튼 [보내진 걸 확인했어요](→ `sent`, 3.2 "보낸 뒤"와 같게) [안 보내졌어요](→ `draft`로 되돌려 다시 보낼 수 있게)를 띄운다. 5분은 동기화 2~3회 시간이다. **(내 판단)**
- **보낸 뒤:**
  - 보낸 메일을 이 업무의 보낸 메일(`OUTBOUND`, Gmail 메일 번호 포함)로 저장한다.
  - 업무는 `WAITING`("답장 보냄"), `reply_sent_at` 기록, 답장 넛지 종료.
  - 남은 할 일이 있으면 "남은 할 일을 완료로 정리할까요? [모두 완료] [그대로 두기]"를 보인다.
  - 타임라인: "답장을 보냈습니다 (받는 사람 1명, 참조 N명)". 본문 · 주소는 남기지 않는다.
- 발송 실패(권한 만료 등)는 초안을 남기고 이유와 해결 방법을 보인다.

## 4. Gmail에서 직접 보낸 답장 감지

- 지금 동기화는 보낸 메일(`SENT`)을 건너뛴다. 6단계에서는 **이미 메일 업무가 있는 스레드의 보낸 메일만** 저장한다. 업무와 관계없는 보낸 메일은 저장하지 않는다. **(내 판단: 개인정보 최소화)**
- LLM은 쓰지 않는다.
- 저장하면: 그 업무를 `WAITING`으로, `reply_sent_at` 기록, 답장 넛지 종료, 남은 할 일 정리 안내(3.2와 같음).
- 앱에서 보낸 메일이 동기화로 다시 들어오면 Gmail 메일 번호로 알아보고 중복 저장하지 않는다.
- 이미 닫힌 업무의 스레드에서 내가 보낸 메일은 저장만 하고 상태는 바꾸지 않는다.
- 같은 스레드에서 내가 보낸 메일 뒤에 상대 메일이 오면 6절 분석 결과에 따라 상태를 정한다(6.5).

## 5. 상대 답장 없음 → 다시 연락할지 묻기

상위 설계 4.9절의 "3일 뒤 자동 완료"를 대체한다(5단계 결정).

- **조건:** `WAITING` 상태이고, 마지막으로 보낸 답장(`reply_sent_at`) 뒤로 상대 메일이 없고, 그로부터 **영업일 3일**이 지났다. 영업일은 사용자 시간대 기준 월~금이다. **(내 판단)**
  - 예: 금요일 오후에 보내면 다음 주 수요일 같은 시각.
- **동작:** 업무를 "처리할 일"로 올리고, 업무 상세 맨 위 안내 띠와 카드 상황 표시 **"보낸 지 영업일 3일째 답이 없습니다"**, 브라우저 알림 한 번(알림 키에 보낸 메일 번호).
  - 버튼: **"다시 연락하기"**(목적 `followup`으로 초안 만들기 입력칸을 연다), **"더 기다리기"**(영업일 3일 더, 다시 `WAITING`), **"완료로 닫기"**.
  - 묶음은 지금 규칙을 따른다(기한 · 중요도 기준).
- 상태 이동은 동기화 주기에서 코드로 한다. LLM 없음.
- 상대 메일이 오면 이 확인은 멈추고 지금처럼 "처리할 일"이 된다.

## 6. 상대 재답장으로 업무 고치기 (상위 설계 12.1 확정)

### 6.1 방식 (내 판단: 분석 1회)
같은 스레드에 상대 메일이 오면(합쳐진 스레드 포함) 분석 1회를 돌린다. 상위 설계 4.6의 Agent 루프 대신이다.
- LLM에 주는 것: 업무의 지금 상태(제목, 한 줄 요약, 상대 요청, 기한과 근거, 할 일 목록)와 **새로 온 메일**(인용 · 전달 부분은 지금처럼 제거한 본문). 앞선 메일은 짧게 맥락으로만.
- LLM이 돌려주는 것(구조화 JSON):
  - `changes`: 항목마다 `field`(title · summary · requests · deadline · todo_add), `before`, `after`, `evidence`(새 메일 원문에서 그대로 옮긴 문장), `kind`(`confirmed` 확정 변경 / `question` 질문 · 제안)
  - `needs_reply`, `suspicious`(지금과 같음)
- 기존 `MAIL_TRIAGE_ENABLED`, 분석 횟수 제한, 실패 처리 규칙을 그대로 따른다.

### 6.2 코드가 거르는 것
- `evidence`가 새 메일 본문에 실제로 없으면 그 변경을 버린다(공백 · 줄바꿈 차이는 무시하고 비교).
- 날짜는 지금처럼 코드로 다시 계산한다(수신 시각 · 사용자 시간대 기준). 틀리면 버린다.
- `kind=question`은 반영하지 않고 "확인 필요"로만 보인다.

### 6.3 반영 규칙
- 제목 · 한 줄 요약 · 상대 요청: 바로 바꾼다.
- 기한: 바로 바꾼다. 단 **사용자가 직접 정한 기한**(근거 "사용자가 직접 정함")이면 바꾸지 않고 "상대가 기한을 10/31로 바꿨습니다 [반영하기]" 제안으로 보인다.
- 중요도: 재답장으로 바꾸지 않는다.
- 할 일: **추가만 한다.** 지우거나 체크 상태를 바꾸지 않는다(상위 설계 12.1).
  - → 2026-10-27 변경(실제 계정 점검, 사용자 결정): 기존 할 일의 내용이 바뀌면 새로 만들지 않고 그 할 일의 제목을 고친다. 메모는 남기고 끝낸 할 일은 체크를 푼다. 지우지는 않는다. [결정 기록](../../decisions.md#내용이-바뀐-할-일은-새로-만들지-않고-고친다-실제-계정-점검-2026-10-27)
- 참고용 업무에 할 일이 생기면 "처리할 일"로 올린다.
- 캘린더: 기한 · 제목이 바뀌면 지금처럼 다시 반영한다.
  - → 2026-10-27 보완: 일정 제목은 한 줄 요약, 설명은 요청 · 할 일로 만들므로 이 값이 바뀌어도 다시 반영한다.

### 6.4 보여 주기
- 업무 상세 요약 카드 안에 **"상대 답장으로 바뀐 내용"** 칸. 항목마다:
  - `수량 100개 → 150개` / 근거 문장 / 보낸 사람(예: "박지은(B상사)") / 받은 시각
  - **[되돌리기]** 버튼: 그 항목만 이전 값으로 돌린다. 되돌린 뒤 사용자가 고친 값이 있으면 그 값을 덮지 않는다.
  - `question`은 "확인 필요 — 상대가 150개도 가능한지 물었습니다"로 보이고 버튼은 없다.
- 가장 최근 재답장의 변경만 펼쳐 보이고, 이전 것은 접는다.
- 타임라인: "기한 10/30 → 10/31", "요청: 수량 100개 → 150개"처럼 전후 값만 한 줄로 남긴다(5단계 로그 규칙: 한 줄 요약까지 허용).
- 카드에 "내용 바뀜" 표시를 붙인다(다음에 상세를 열 때까지). **(내 판단)**

### 6.5 재답장 뒤 업무 상태
- 답장이 필요하거나(`needs_reply=true`), 확정 변경이나 새 할 일이 있으면 → "처리할 일"(지금과 같음).
- **답장이 필요 없고 변경 · 새 할 일도 없으면**(예: "감사합니다") → `WAITING`("답장 보냄")에 그대로 두고, 업무 상세에 "상대가 답장했습니다(답장 필요 없음) [완료로 닫기]"를 띄운다. 5절 "답 없음" 확인은 멈춘다. **(사용자 결정)**
- 분석이 실패했거나 판별이 꺼져 있으면 지금처럼 "처리할 일"로 올린다(안전한 쪽).

### 6.6 분석 대상 (내 판단)
- 분석 대기 · 분석 실패 업무에 새 메일이 오면 6절 변경 분석이 아니라 **처음 분석**(접수 분석)을 스레드 전체로 다시 한다.
- 한 동기화 주기에 같은 업무로 여러 통이 오면 **묶어서 한 번만** 분석한다.

## 7. 다른 스레드로 온 수정 요청 알아보기

### 7.1 후보 고르기 (코드)
- 새로 접수된 메일 업무와 **보낸 사람 주소가 같거나 같은 회사 주소**(도메인이 같고, 무료 메일 도메인이 아님)이며, 처리할 일 · 답장 보냄 상태이고, 14일 안에 만들어진 다른 업무. 최근 것부터 최대 3개.
- 무료 메일 도메인 목록은 코드에 둔다(gmail.com, naver.com, daum.net, hanmail.net, kakao.com, outlook.com, hotmail.com, yahoo.com, icloud.com, nate.com 등). **(내 판단)**
- 5단계의 "같은 보낸 사람" 합치기 후보 규칙을 이것으로 바꾼다.

### 7.2 내용 판단 (LLM, 분석 호출에 함께)
- 후보가 있으면 새 메일을 분석하는 **같은 호출**에 후보 업무의 번호 · 제목 · 한 줄 요약을 함께 준다. 호출 수는 늘지 않는다.
- LLM은 `related_task`: 후보 번호 하나 또는 없음, `relation`: `change`(수정 · 추가 요청) / `followup`(같은 건의 이어지는 연락) / `none`, `evidence`(새 메일 원문 문장)를 돌려준다.
- `evidence`가 원문에 없거나 `none`이면 제안하지 않는다.
- 판단 부분은 함수 하나 뒤에 둬서 나중에 다른 모델(예: Jev)로 바꿀 수 있게 한다. **(사용자 결정)**

### 7.3 보여 주기
- 판단이 있으면: 새 업무 상세 맨 위 안내 띠 **"업무 #12(견적서 요청)의 수정 요청으로 보입니다 — '앞서 김민수 과장이 요청드린 수량을 150개로…'"** [이 업무에 합치기] [따로 두기]. 카드에는 "합치기 제안".
- 판단이 없으면 합치기 제안을 띄우지 않는다. **같은 보낸 사람이어도 LLM이 관계없다고 하면 띄우지 않는다.** **(내 판단: 사용자는 "같은 회사라서 뜨는 제안"을 줄이고 싶어 했다. 놓쳐도 별도 업무로 남을 뿐이다)**
  - 예외: 분석이 실패했거나 판별이 꺼져 있으면 5단계처럼 "같은 보낸 사람" 규칙만으로 제안한다.
- **합치면 (내 판단)**
  - 메일 · 할 일은 5단계 규칙대로 옮긴다(할 일은 중복 제목 제외 추가).
  - **상대 요청 · 기한 · 한 줄 요약은 5단계의 "합집합 · 이른 기한" 규칙 대신 6절 "바뀐 내용 찾기" 결과로 고친다.** 그래야 "100개"와 "150개"가 함께 남거나 연기된 기한이 무시되지 않는다. 중요도는 5단계처럼 높은 쪽.
  - 분석은 합치기 요청 안에서 기다리지 않고 워커가 바로 이어서 한다(동기화 깨우기). 그동안 A에는 "합친 내용을 분석하는 중" 표시.
  - 판별이 꺼져 있거나 분석이 실패하면 5단계 규칙(합집합 · 이른 기한)으로 마무리한다.
  - 되돌리기(10분)는 합치기 직전 상태로 돌리며 분석으로 바뀐 내용도 함께 되돌린다. 되돌린 뒤 도착한 분석 결과는 버린다(업무를 다시 읽어 합쳐진 상태가 아니면 버리는 5단계 방식).
- **판단 결과 보관 (내 판단):** "수정 요청으로 보임" 판단(대상 업무 · 근거)은 접수 때 업무에 저장한다. 화면을 열 때마다 다시 계산하지 않고, 다시 분석할 때만 새로 판단한다. 판단을 못 했으면(실패 · 꺼짐) 그 사실도 저장해서 7.3의 예외 규칙을 적용한다.

## 8. 기한을 없애면 캘린더 일정 지우기 (사용자 결정)

- 앱이 만든 일정(업무 표식이 있는 일정)만 지운다. 표식이 없거나 다른 사람 것이면 지우지 않는다.
- 사용자가 이미 캘린더에서 지웠으면(404 · `cancelled`) 조용히 끝낸다.
- 지운 뒤 `calendar_state`는 `none`, 일정 번호를 비운다. 다시 기한을 넣으면 새로 만든다.
- 5단계의 "캘린더 일정은 그대로 남습니다…" 안내를 없앤다.
- 업무가 닫힐 때는 지금처럼 지우지 않고 ✓를 붙인다(변경 없음).
  - → 2026-10-27 변경(실제 계정 점검, 사용자 결정): 완료 · 취소 · 합쳐진 업무의 일정도 지운다. 다시 열리면 되살린다. 이미 ✓만 붙은 일정도 지운다. [결정 기록](../../decisions.md#닫힌-업무의-일정은-지운다-실제-계정-점검-2026-10-27)

## 9. 정확도 측정 (사용자 결정)

- **가상 메일 시험 세트**(실제 메일 아님, `backend/smoke/` 아래)를 만든다.
  - 재답장 변경 감지 약 10건: 분명한 변경, 인용이 섞인 메일, 질문형, 여러 항목 동시 변경, 변경 없는 감사 인사(정답: 변경 없음 · 답장 불필요 → 6.5), 다른 직원이 보낸 전체 답장
  - 다른 스레드 수정 요청 판단 약 10건: 앞 업무를 언급하는 수정, 언급 없는 수정, 같은 회사의 다른 요청, 같은 보낸 사람의 새 요청, 후보 여러 개 중 하나
  - 답장 초안 약 5건: 메모가 충분한 경우, 메모가 부족한 경우(빈칸이 나와야 함), 본문에 주입 문장이 있는 경우
- 메일마다 정답을 정해 두고, 실제 LLM으로 돌려 표로 보인다.
  - 판단: 맞게 제안한 비율, 놓친 비율, 잘못 제안한 비율
  - 변경 감지: 맞게 찾은 변경, 놓친 변경, 잘못 반영한 변경(특히 질문 · 인용을 확정으로 본 경우)
  - 초안: 근거 없는 숫자 · 날짜 수, 빈칸이 필요한데 안 남긴 경우
- 실행은 opt-in 스모크(`RUN_LLM_SMOKE=1`)와 같은 방식. 결과 표는 구현 보고와 `docs/`에 남긴다.
- **통과 기준 (내 판단):** "잘못 반영한 변경"과 "근거 없는 사실이 든 초안"은 0건이 목표다. 나오면 프롬프트를 고치고 다시 잰다. 제안 · 감지를 놓친 비율은 기록만 하고 막지 않는다(놓쳐도 데이터가 망가지지 않으므로).

## 10. 데이터 · API · 개인정보 (방향만, 이름은 구현이 정함)

- **업무:** `reply_sent_at`, 상대 답장 없음 확인 시각(더 기다리기 기준), 재답장 변경 기록(항목별 전후 값 · 근거 · 보낸 메일 번호 · 되돌림 여부), "내용 바뀜" 표시.
- **초안:** 업무당 하나. 받는 사람 · 참조 후보 · 제목 · 본문 · 상태(`draft`/`sending`/`sent`/`failed`/`unknown`) · 경고. 기존 `ApprovalRequest`는 Agent 실행에 묶여 있으므로 메일 업무 초안에는 쓰지 않는다. **(내 판단)**
- **메일:** 업무 스레드의 보낸 메일 저장(4절).
- **API:** 초안 만들기, 초안 고치기, 보내기, 초안 지우기, 남은 할 일 모두 완료, 상대 답장 없음 선택(다시 연락 · 더 기다리기 · 완료), 변경 되돌리기 · 기한 제안 반영. 모두 로그인 확인, POST, LLM을 부르는 것은 호출 횟수 제한.
- **알림:** 5단계 알림 목록에 "상대 답장 없음"을 더한다.
- **개인정보 (`docs/privacy.md` 갱신):**
  - LLM으로 새로 가는 것: 답장 초안용 스레드 메일 · 할 일 메모 · 사용자 입력, 재답장 분석용 업무 상태, 수정 요청 판단용 후보 업무 3개의 제목 · 요약.
  - 새로 저장하는 것: 업무 스레드의 보낸 메일, 초안.
  - 발송: 사용자가 누를 때만, 서버가 정한 수신자에게만.

## 11. 남은 위험 · 나중에 검토

- **답장 감지 지연:** 동기화 주기(90초) 동안은 Gmail에서 직접 보낸 답장을 모른다.
- **공휴일:** 영업일 계산에 공휴일이 없다. 명절에는 "답이 없습니다"가 일찍 뜬다.
- **판단 정확도:** 9절 측정 결과에 따라 프롬프트를 고친다. 애매한 메일은 놓칠 수 있다(별도 업무로 남음).
- **무료 메일 도메인 목록:** 목록에 없는 개인 도메인은 같은 회사로 볼 수 있다. LLM 판단이 한 번 더 거른다.
- **나중에 검토:**
  - 업무가 수백 개로 늘면 임베딩으로 후보를 고르고 LLM이 판단하는 방식
  - 판단 전용 모델(TypeSafe Jev 등)로 7.2 교체. 9절 세트로 비교한 뒤 결정
  - 첨부파일 발송, HTML 서식

## 12. 상위 설계에 반영할 것

- 4.6: 재답장은 Agent 루프 대신 분석 1회(6절). 내가 직접 답장한 경우는 4절.
- 4.8: 초안은 1회 호출, 사실은 사용자 입력만, 빈칸 표기, 받는 사람은 가장 최근 받은 메일의 보낸 사람.
- 4.9: 답장 보냄 영업일 3일 → 다시 연락할지 묻기(5절).
- 4.7: 기한을 없애면 앱이 만든 일정을 지운다(8절).
- 12.1: 확정됨 — 이 문서 6절.
- 5단계 설계 4.3 합치기 후보: 같은 회사 주소 + LLM 판단(7절).
