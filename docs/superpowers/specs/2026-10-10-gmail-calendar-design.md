# Gmail · Google 캘린더 연동: 메일 중심 업무 Agent 설계

- 작성일: 2026-10-10
- 상태: 사용자 검토 대기
- 대상 저장소: `ahcy205/FollowUp_agent`

## 1. 목적

지금의 FollowUp Agent는 사용자가 목표를 입력해야 일을 시작하고, 메일과 고객 데이터는 가상이다.
이 설계는 서비스의 출발점을 **받은편지함에 들어온 업무 메일**로 바꾼다.

사용자가 원하는 흐름:

1. 업무 메일이 오면 내용을 정리해서 보여준다. 상대가 원하는 것과 내가 할 일을 이해하기 쉽게 요약한다.
2. 메일에 기한이 있으면 Google 캘린더에 일정을 넣고, 캘린더 알림과 앱 안의 남은 기간 표시로 알려준다.
3. 할 일을 끝내면 처리 내용을 바탕으로 답장을 써 주고, 사용자가 승인하면 원래 스레드에 발송한다.

### 확정된 결정

| 항목 | 결정 |
|---|---|
| 메일 · 캘린더 | Gmail, Google 캘린더 |
| 사용자 | 당분간 본인 한 명. Google 앱은 테스트 상태로 시작 |
| 처리 범위 | 받은편지함 전체를 보고 업무 메일만 자동 판별 |
| 새 메일 감지 | 90초 주기 확인. 감지부는 나중에 Gmail 푸시로 교체할 수 있게 분리 |
| 알림 | Google 캘린더 팝업 알림 + 앱 안 남은 기간 표시와 브라우저 알림 |
| 답장 | 앱 승인 카드에서 승인하면 Gmail로 원래 스레드에 바로 발송 |
| 기존 기능 | 메일 중심으로 전환. 목표 입력은 보조 기능, 가상 데이터와 시뮬레이터는 데모 모드에서만 |
| Agent 사용 범위 | 새 메일 접수는 정해진 순서의 파이프라인, 판단이 필요한 재답장 처리와 답장 작성에만 Agent 루프 |

### 범위 밖

- 첨부파일 내용 분석 (이름만 저장)
- Gmail 푸시 알림(Pub/Sub)
- 캘린더에서 사용자가 옮긴 일정 날짜를 앱으로 역반영
- 여러 Google 계정 동시 연결
- 공개 서비스용 Google 앱 심사

## 2. 전체 구조

```
                      ┌────────────── FastAPI 프로세스 1개 ──────────────┐
브라우저 ── REST ────▶│ API (인증·CSRF·소유권)                            │
        ◀── SSE ─────│ SSE 스트림 (업무 상세 실시간)                       │
                      │                                                  │
                      │ MailSync 스레드 (90초) ──▶ Gmail API (읽기)        │
                      │   ├ 파싱 · 규칙 필터                               │
                      │   ├ 업무 판별 (가벼운 모델, 10통 묶음)  ──▶ LLM     │
                      │   └ 접수 파이프라인 (분석 1회)          ──▶ LLM     │
                      │        └ 캘린더 동기화          ──▶ Calendar API   │
                      │                                                  │
                      │ Agent 오케스트레이터 (기존 루프)       ──▶ LLM     │
                      │   ├ 스레드 재답장 판단                              │
                      │   └ 답장 작성 ─ 승인 카드 ─▶ Gmail API (발송)        │
                      └──────────────────────────────▶ DB ◀───────────────┘
```

외부 API 호출은 모두 `GoogleClient` 인터페이스 뒤에 둔다. 실제 구현은 httpx로 Google REST API를 호출하고,
테스트에서는 메모리 안의 가짜 Gmail · 캘린더(`FakeGoogle`)로 바꿔 끼운다. LLM의 `ScriptedLLM`과 같은 방식이다.

## 3. 데이터 모델

### 새 테이블 `google_accounts` (사용자당 1행)

| 컬럼 | 설명 |
|---|---|
| `user_id` | 고유 |
| `google_email` | 연결한 Gmail 주소 |
| `refresh_token_enc` | AES-GCM으로 암호화한 갱신 토큰. 키는 환경변수 `GOOGLE_TOKEN_KEY` |
| `scopes` | 받은 권한 목록 |
| `history_id` | 마지막으로 처리한 Gmail 변경 지점 |
| `last_synced_at`, `last_sync_error` | 확인 시각과 마지막 오류 |
| `status` | `connected` / `reauth_required` / `disconnected` |
| `sync_lease_until` | 동시에 두 곳에서 동기화하지 않도록 잡는 DB 임대 시각 |

### `emails` 확장

| 컬럼 | 설명 |
|---|---|
| `gmail_message_id` | (`user_id`, `gmail_message_id`) 고유 제약. 중복 처리 방지 |
| `gmail_thread_id` | 스레드 연결, 답장 대상 |
| `rfc_message_id` | 답장의 In-Reply-To · References 헤더용 |
| `cc` | 참조 주소 목록 |
| `received_at` | 메일 수신 시각 |
| `triage` | `pending` / `work` / `not_work` / `filtered` |
| `triage_reason` | 판정 이유 한 줄 |
| `attachments` | 첨부 이름 목록 |

본문(`content`)은 인용과 전달 부분을 제거한 텍스트를 최대 2만 자까지 저장한다.
방향(`direction`)은 기존 값을 쓰고, Gmail에서 내가 직접 보낸 메일은 `OUTBOUND`로 저장한다.

### `tasks` 확장

| 컬럼 | 설명 |
|---|---|
| `gmail_thread_id` | 연결된 스레드. 메일 업무는 스레드당 업무 1개 |
| `brief` | JSON. `summary`(한 줄 요약), `requests`(상대가 원하는 것 목록), `priority`, `counterpart`(이름, 주소) |
| `deadline_at`, `deadline_all_day` | 기한. 시각이 없으면 하루 종일 |
| `deadline_kind` | `explicit` / `estimated` / `none` |
| `deadline_source` | 기한의 근거가 된 메일 문장 |
| `calendar_event_id`, `calendar_state` | 일정 번호와 상태 (`synced` / `deleted_by_user` / `none` / `error`) |
| `reply_sent_at` | 답장을 보낸 시각. 자동 완료 판단에 사용 |

할 일 목록은 기존 `plan` 필드를 그대로 쓴다. 항목 구조를 `{id, title, done, evidence, due_at?, source}`로 넓힌다.
메일 업무에서 `evidence`는 사용자의 처리 메모이고, `source`는 `agent` 또는 `user`다.

`origin`에 `mail` 값을 추가한다.

### 새 테이블 `contacts`

메일을 주고받은 상대를 자동 저장한다. 보조 기능인 목표 입력에서 수신자를 고를 때 쓴다.
기존 `customers` 테이블은 데모 모드 데이터로만 남긴다.

## 4. 처리 흐름

### 4.1 Google 연결

1. 설정 화면의 "Google 계정 연결"을 누르면 서버가 `state`(세션 결합, 1회용)를 만들고 Google 동의 화면으로 보낸다.
2. 권한: `gmail.readonly`, `gmail.send`, `calendar.events`, `openid email`. 메일 삭제 · 수정 권한은 받지 않는다.
3. 콜백에서 코드로 토큰을 받아 갱신 토큰을 암호화 저장하고, 첫 동기화로 최근 3일치를 가져온다.
4. 해제 시 Google 토큰 취소 엔드포인트를 호출하고 토큰을 지운다. "저장된 메일 본문도 삭제" 선택지를 둔다.
5. 갱신이 `invalid_grant`로 실패하면 `reauth_required`로 바꾸고 앱 상단 배너와 브라우저 알림으로 다시 연결을 요청한다.
   테스트 상태 앱은 갱신 토큰이 7일 뒤 만료되므로 이 경로가 주기적으로 발생한다.

### 4.2 주기 확인 (90초)

1. `sync_lease_until`로 임대를 잡은 계정만 처리한다. 여러 프로세스가 떠도 한 곳만 동기화한다.
2. `history.list(startHistoryId, historyTypes=messageAdded)`로 새 메일을 가져온다.
3. 404(변경 기록 범위 초과)면 `last_synced_at` 이후를 `messages.list(q="after:...")`로 다시 훑는다. 이미 저장한 메일 번호는 건너뛴다.
4. 각 메일에 대해:
   - 내가 보낸 메일이고 업무 스레드에 속하면 4.6의 "내가 직접 답장함" 처리로 넘긴다.
   - 받은 메일이고 업무 스레드에 속하면 4.6의 "상대 재답장" 처리로 넘긴다.
   - 그 밖의 받은 메일은 파싱 후 판별 대기열에 넣는다.
   - 업무 스레드가 아닌 내가 보낸 메일은 저장하지 않는다. 받는 사람만 `contacts`에 기록한다.
   - 받은 메일의 보낸 사람도 `contacts`에 기록한다 (판별 결과와 무관).
5. `history_id`와 `last_synced_at`을 갱신한다.

### 4.3 업무 메일 판별

1. **규칙 필터 (LLM 호출 없음).** 다음은 `filtered`로 끝낸다.
   - Gmail 분류가 프로모션 · 소셜 · 업데이트 · 포럼
   - `List-Unsubscribe` 또는 `Precedence: bulk` 헤더
   - `no-reply`, `noreply`, `mailer-daemon` 류 발신자
2. **묶음 판별.** 남은 메일을 최대 10통씩 묶어 가벼운 모델(`LLM_ANALYSIS_MODEL`)로 한 번에 판정한다.
   각 메일의 보낸 사람, 제목, 본문 앞 1,500자만 보낸다. 결과는 메일별 `work`/`not_work`와 이유 한 줄.
3. LLM 한도나 오류면 `pending`으로 남기고 다음 주기에 다시 시도한다.
4. 사용자가 `not_work` 메일에서 "업무로 처리"를 누르면 `work`로 바꾸고 4.4를 실행한다.

### 4.4 접수 파이프라인 (업무 메일 1통)

LLM 분석을 1회 호출해 구조화 결과를 받는다.

```
summary          한 줄 요약
counterpart      상대 이름, 소속
requests[]       상대가 원하는 것
todos[]          내가 할 일 {title, due_text?}
deadline         {text, date?, time?, kind: explicit|estimated|none}
priority         HIGH|NORMAL|LOW
needs_reply      답장이 필요한지
suspicious[]     AI에게 지시하려는 문장 (따르지 않음)
```

이후 처리는 코드가 한다.

1. 기한 정규화 (4.5).
2. 업무 생성: `origin=mail`, 상태 `ACTION_REQUIRED`, 할 일 목록, `brief`.
   `needs_reply=false`이고 할 일이 없으면 상태를 "참고용"(`PENDING`)으로 두고 "답장 필요 없음으로 닫기"를 강조한다.
3. 기한이 있으면 캘린더 동기화 (4.7).
4. 타임라인에 접수 기록을 남긴다. 로그에는 메일 번호와 요약만 남긴다 (6절).

### 4.5 기한 정규화

- 기준 시각은 **메일 수신 시각**, 시간대는 `USER_TIMEZONE`(기본 `Asia/Seoul`).
- LLM은 원문 표현(`text`)과 해석한 날짜를 함께 낸다. 코드가 날짜를 다시 검증한다.
  - 날짜가 수신일보다 과거면 기한으로 잡지 않고 할 일 메모로 남긴다.
  - "다음 주 중", "이번 달 안" 같은 범위 표현은 범위의 마지막 날로 잡고 `estimated`로 표시한다.
  - 시각이 없으면 하루 종일 일정.
- 한 메일에 기한이 여럿이면 가장 이른 날을 업무 기한으로, 나머지는 해당 할 일의 `due_at`으로 둔다.
- 사용자가 화면에서 기한을 고치거나 추정 기한을 확인하면 `explicit`으로 바꾼다.

### 4.6 같은 스레드의 새 메일

**상대 재답장.** 메일을 업무에 붙이고 Agent 루프를 `thread_reply` 트리거로 실행한다.
완료나 취소된 업무였다면 먼저 `ACTION_REQUIRED`로 다시 연다.
Agent가 쓸 수 있는 도구:

| 도구 | 하는 일 |
|---|---|
| `check_email`, `analyze_email` | 기존과 같음 (이 스레드 한정) |
| `update_deadline` | 기한 변경. 캘린더 동기화가 뒤따름 |
| `add_todo`, `complete_todo` | 할 일 추가, Agent가 확인한 일 완료 표시 |
| `update_task_status` | 기존과 같음 |

**내가 직접 답장함** (Gmail 앱 등에서 보낸 경우). LLM 호출 없이 처리한다.
메일을 업무에 붙이고 `reply_sent_at`을 기록해 상태를 "답장 보냄"으로 바꾼다.
할 일이 남아 있으면 업무 상세에 "남은 할 일을 완료로 정리할까요?" 안내를 띄운다.

### 4.7 캘린더 동기화

- 기준은 앱이다. 기한이 생기거나 바뀌면 일정을 만들거나 고친다.
- 일정: 제목 `[업무] {한 줄 요약}`, 추정 기한이면 앞에 `(확인 필요)`. 설명에 상대, 할 일 목록, 앱 업무 링크.
- 알림: 팝업, 하루 전과 1시간 전. 하루 종일 일정은 하루 전 오전 9시.
- 수정 시 일정이 삭제된 상태(404 또는 `cancelled`)면 다시 만들지 않고 `deleted_by_user`로 표시한다.
- 업무가 완료되거나 취소되면 일정은 지우지 않고 제목 앞에 `✓`를 붙인다.
- 캘린더 오류는 업무 처리를 막지 않는다. `calendar_state=error`와 "다시 시도" 버튼으로 노출한다.

### 4.8 답장 작성과 발송

1. 사용자가 "답장 초안 만들기"를 누르면 Agent 루프를 `reply_requested` 트리거로 실행한다.
   맥락에는 **이 스레드의 메일과 이 업무의 할 일 · 처리 메모만** 넣는다.
2. Agent는 `draft_reply(body, subject?)`를 호출한다. 수신자 인자는 없다.
   서버가 수신자를 원래 메일의 보낸 사람으로 정하고, 원래 참조 목록은 후보로만 둔다.
3. `send_reply`는 승인 필요 도구다. 승인 카드에 수신자, 참조 체크박스, 제목, 본문이 나오고 기존처럼 편집 후 승인할 수 있다.
4. 초안에 스레드에 없던 이메일 주소나 전화번호가 있으면 승인 카드에 경고를 띄운다.
5. 승인하면 Gmail `messages.send`에 `threadId`, `In-Reply-To`, `References`, `Re:` 제목을 넣어 발송한다.
6. 발송 후 상태는 "답장 보냄".

### 4.9 업무 상태

| 화면 표시 | 내부 상태 | 들어가는 조건 |
|---|---|---|
| 처리할 일 | `ACTION_REQUIRED` | 업무 메일 접수, 상대 재답장, 재오픈 |
| 진행 중 | `IN_PROGRESS` | Agent 실행 중 |
| 답장 보냄 | `WAITING` (`waiting_for="상대 회신"`) | 앱 또는 Gmail에서 답장 발송 |
| 참고용 | `PENDING` | 답장 · 할 일이 필요 없다고 분석된 메일 |
| 완료 | `COMPLETED` | 사용자가 닫음. (답장 보냄 3일 뒤에는 자동 완료 대신 "다시 연락할까요?"를 묻는다 — 5단계 설계 4.2절, 6단계에서 연결) |
| 취소됨 | `CANCELLED` | 사용자 취소 |

- "답장 필요 없음으로 닫기"는 완료로 바꾸고 이유를 기록한다.
- ~~3일 자동 완료~~ → 2026-10-26 변경: 답장 보냄 상태로 3일간 상대 메일이 없으면 업무를 "처리할 일"로 올리고 다시 연락할지 묻는다(6단계).
- 메일 업무의 완료 조건은 기존 "하위 목표 전부 달성" 대신 위 표를 따른다. 목표 입력 업무는 기존 규칙을 유지한다.

## 5. 화면

### 받은 업무 (메인)

- 상단 한 줄: 연결 상태, 마지막 확인 시각, "지금 확인" 버튼. 재연결이 필요하면 빨간 배너.
- 탭: 처리할 일 / 답장 보냄 / 참고용 / 완료.
- 정렬: "지금 처리 → 이번 주 → 나중에" 묶음, 묶음 안에서는 중요도 → 기한 → 받은 순. 스누즈, 답장 넛지, 업무 합치기 포함. **자세한 화면 설계는 `2026-10-26-inbox-screen-design.md`를 따른다.**
- 카드: D-day 배지(지남 빨강, 3일 이내 주황), 보낸 사람, 제목, 한 줄 요약, 할 일 진행도, 상태.
- 맨 아래 접힌 영역: "업무 아님으로 분류된 메일 N건", 펼치면 이유와 "업무로 처리" 버튼.

### 업무 상세

- **요약 카드:** 한 줄 요약, 상대가 원하는 것, 기한과 남은 기간, 근거 문장, 캘린더에서 열기, 기한 수정. 추정 기한이면 "확인 필요"와 확인 버튼.
- **할 일 체크리스트:** 항목별 체크와 처리 메모, 항목 추가와 삭제, 항목별 기한 표시.
- **답장 초안 만들기:** 할 일을 다 끝내면 강조. 남은 할 일이 있으면 누를 때 알려준다.
- 승인 카드, 접힌 원본 스레드, 오른쪽 타임라인과 토큰 사용량은 기존과 같다.
- "답장 필요 없음으로 닫기", "업무 취소".

### 설정

- Google 연결 · 해제, 받은 권한, 마지막 확인, 오류 안내, 해제 시 본문 삭제 선택.
- 브라우저 알림 허용 버튼.

### 보조 기능

- "새 업무 직접 만들기"(기존 목표 입력)는 메뉴 안쪽으로 옮긴다. 수신자는 `contacts`에서 고른다.

### 앱 안 알림

- 앱이 열려 있으면 1분마다 기한을 확인해 D-1과 당일에 브라우저 알림을 한 번씩 띄운다.
  보낸 알림 기록은 브라우저 저장소에 둔다.
- 처리할 일 개수를 탭 제목에 표시한다.

## 6. 보안

- **수신자 고정:** 답장 수신자는 서버가 원래 메일에서 정한다. Agent는 수신자를 지정할 수 없다. 메일 본문 속 주소 지시는 무시한다.
- **맥락 격리:** 답장 작성과 재답장 판단에는 해당 스레드만 넣는다. 다른 업무의 메일은 넣지 않는다.
- **유출 경고:** 초안에 스레드 밖 연락처가 있으면 승인 카드에 경고. 기존 고객 기반 차단은 데모 모드에만 남긴다.
- **프롬프트 주입:** 모든 메일 본문은 기존처럼 `<untrusted_external_content>`로 감싸고 정규식 탐지를 유지한다.
  판별 · 분석 결과의 `suspicious`는 타임라인 보안 경고로 남기고 할 일로 만들지 않는다.
- **로그 최소화:** 메일 관련 도구의 로그 입출력에서 본문을 빼고 메일 번호, 요약, 길이만 남긴다.
- **토큰:** 갱신 토큰은 `GOOGLE_TOKEN_KEY`로 AES-GCM 암호화. 키가 없으면 Google 연결 기능을 끈다. 접근 토큰은 메모리에만 둔다.
- **OAuth state:** 세션에 묶인 1회용 값, 10분 만료. 콜백 주소는 `PUBLIC_URL` 기준으로 고정한다.
- **권한 최소화:** 읽기, 발송, 캘린더 일정만 받는다.
- **저장소 공개 상태:** Google 클라이언트 비밀값과 키는 환경변수로만 받는다. `.env.example`에는 이름만 둔다.

## 7. 오류 처리

| 상황 | 처리 |
|---|---|
| 갱신 토큰 만료 · 취소 | `reauth_required`, 동기화 중지, 배너와 브라우저 알림 |
| Gmail 변경 기록 범위 초과 (404) | 날짜 조건 재동기화, 중복은 메일 번호로 제거 |
| Gmail · Calendar 429, 5xx | 지수 대기 후 다음 주기에 재시도, 연속 실패는 `last_sync_error`에 표시 |
| LLM 한도 · 오류 (판별) | `pending` 유지, 다음 주기 재시도 |
| LLM 한도 · 오류 (분석) | 메일은 `work`, 업무는 "분석 대기"로 만들고 "다시 분석" 버튼 |
| 캘린더 일정이 사용자에 의해 삭제됨 | 재생성하지 않고 `deleted_by_user` 표시 |
| 발송 실패 | 승인 카드를 다시 열고 오류 표시, 업무 상태는 그대로 |
| 서버 재시작 | 기존 `recover_stale_runs` 유지, 동기화 임대는 시간 만료로 자연 해제 |

## 8. 설정과 환경변수

| 변수 | 설명 |
|---|---|
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | Google Cloud OAuth 클라이언트 |
| `GOOGLE_TOKEN_KEY` | 갱신 토큰 암호화 키 (32바이트, base64) |
| `MAIL_SYNC_INTERVAL_SECONDS` | 기본 90 |
| `MAIL_BACKFILL_DAYS` | 첫 연결 백필, 기본 3 |
| `AUTO_COMPLETE_DAYS` | 답장 후 자동 완료, 기본 3 |
| `USER_TIMEZONE` | 기본 `Asia/Seoul` |
| `DEMO_MODE` | 가상 데이터 · 시뮬레이터 · Demo Reset 노출. 개발 기본 `true`, 운영 기본 `false` |

새 의존성: `cryptography`(토큰 암호화). Google API는 httpx로 직접 호출해 무거운 클라이언트 라이브러리를 피한다.

## 9. 테스트

- **단위:** MIME 파싱과 인용 제거, 규칙 필터, 기한 정규화(수신일 기준, 범위 표현, 과거 날짜, 시간대), 토큰 암호화 왕복.
- **통합 (`FakeGoogle` + `ScriptedLLM`):**
  - 첫 연결 백필 → 판별 → 업무 생성 → 캘린더 일정 생성
  - 변경 기록 404 → 재동기화, 중복 없음
  - 상대 재답장 → 업무 재오픈과 기한 변경
  - Gmail에서 직접 답장 → 답장 보냄 → 3일 후 자동 완료
  - 답장 초안 → 수신자 고정 확인 → 승인 → 스레드 헤더가 붙은 발송
  - 사용자가 캘린더 일정을 지운 뒤 기한 변경 → 재생성 안 함
  - 토큰 만료 → `reauth_required`
  - 다른 사용자의 업무 · 메일 접근 404 (기존 격리 테스트 확장)
- **실제 계정 확인 (opt-in):** 기존 스모크 테스트처럼 `RUN_GOOGLE_SMOKE=1`일 때만 본인 계정으로 연결, 목록 조회, 테스트 일정 생성 후 삭제.
- **로컬 브라우저 점검:** 각 단계 완료 시 실제 Gmail 계정으로 화면을 직접 눌러 확인한 뒤 커밋한다.

## 10. 구현 단계

각 단계는 독립적으로 테스트와 브라우저 점검을 마치고 커밋한다.

1. **Google 연결:** OAuth, 토큰 암호화, 설정 화면, 재연결 배너.
2. **메일 동기화:** 주기 확인, 백필, 404 재동기화, 임대, 파싱, 내가 보낸 메일 인식.
3. **판별과 접수:** 규칙 필터, 묶음 판별, 분석, 기한 정규화, 업무 · 할 일 생성.
4. **캘린더:** 일정 생성 · 수정, 삭제 감지, 알림 설정.
5. **화면:** 받은 업무, 업무 상세 요약 카드와 할 일, 업무 아님 목록, 앱 안 알림.
6. **답장과 수명주기:** 답장 도구, 승인 카드 확장, 스레드 발송, 재답장 Agent, 자동 완료, 답장 필요 없음.
7. **정리:** 로그 최소화, 유출 경고, 데모 모드 분리, 목표 입력 보조화와 `contacts`.

## 11. 남은 위험

- **7일 재연결:** 테스트 상태로 쓰는 동안 매주 다시 연결해야 한다. 앱을 프로덕션 상태로 바꿀지는 사용해 보며 결정한다.
- **LLM 한도:** 메일이 많은 날은 판별이 밀릴 수 있다. 규칙 필터와 묶음 판별로 줄이되, 유료 등급 전환 여부는 사용량을 보고 정한다.
- **상시 서버 필요:** 주기 확인은 서버가 켜져 있어야 동작한다. 실사용을 시작하는 시점에 상시 배포가 필요하다.
- **분석 품질:** 요약과 기한 추출은 LLM 품질에 좌우된다. 추정 기한 표시와 사용자 수정 경로로 보완한다.

## 12. 다음 설계 때 확정할 항목 (실사용 피드백, 2026-10-26)

3단계 실제 계정 확인 중에 사용자가 낸 의견입니다. **아직 확정된 설계가 아닙니다.** 5 · 6단계 설계를 시작할 때 문구와 범위를 사용자와 확정하고 위 절에 반영합니다.

### 12.1 재답장으로 업무 내용 갱신 (6단계, 4.6절 보완)

- **문제:** 같은 스레드에 상대가 내용을 바꾸는 답장(예: "수량을 100개 → 150개로")을 보내도 업무의 제목 · 요약 · 상대 요청은 처음 분석 그대로 남는다. 4.6절의 Agent 도구에는 기한과 할 일만 있고 요약과 요청을 고치는 도구가 없다.
- **방향:**
  - Agent 도구에 `update_brief`(제목, 한 줄 요약, 상대 요청 갱신)를 추가한다.
  - 바뀐 내용은 타임라인에 "변경 전 → 변경 후"로 남긴다. 예: "기한 10/30 → 10/31", "요청: 수량 100개 → 150개".
  - 할 일은 지우지 않고 추가 · 완료만 한다. 사용자가 체크한 상태를 보존하기 위해서다.
  - 참고용 업무에 할 일이 생기면 "처리할 일"로 올린다.
- **확정할 것:** Agent 루프로 할지, 재분석 1회로 할지. 재분석 1회는 단순하고 저렴하다.

### 12.2 같은 상대의 새 메일을 기존 업무와 합치기 — **확정됨: 5단계 설계 4.3절** (2026-10-26)

- **문제:** 같은 상대가 같은 건으로 답장이 아닌 새 메일(예: 수정 요청)을 보내면 Gmail에서 새 스레드가 되어 업무가 따로 생긴다. 지금 설계는 스레드가 다르면 무조건 별개 업무다.
- **방향:**
  - 새 스레드 메일이 들어올 때, 같은 상대의 진행 중 업무가 있으면 "기존 업무에 합치기"를 제안한다.
  - 합치기는 사용자가 확인해야 실행한다. 엉뚱한 업무에 붙으면 답장 대상과 맥락이 섞이기 때문이다.
  - 합친 업무는 스레드를 여러 개 가질 수 있어야 한다(현재는 업무당 스레드 1개). 답장은 마지막으로 받은 스레드에 보낸다.
- **확정할 것:**
  - 제안 방식: 화면 버튼만 둘지, 접수 분석 때 LLM이 같은 건인지 판단해 제안까지 할지
  - 데이터 구조: 업무-스레드 연결 테이블 추가 여부
