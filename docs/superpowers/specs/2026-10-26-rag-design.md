# 1부. Agent 전체 구조

## 1.1 한 줄 정의

업무 하나를 맡으면 끝날 때까지 실행하고, 멈추고, 기다리고, 새 이벤트가 오면 다시 판단하는 **업무 후속조치 Agent**.
판단은 실제 LLM이 하고, 실행 여부는 서버가 정한다.

## 1.2 실행 단위

| 단위 | 의미 |
|---|---|
| **업무(Task)** | 사용자가 신경 써야 할 일 하나. 상태, 할 일 목록, 기한, 연결된 메일을 가진다. 며칠에 걸쳐 이어진다. |
| **실행(Run)** | 이벤트 하나에 대한 Agent의 한 번의 작업. 대화 기록 전체를 DB에 저장해 승인 대기에서 멈췄다가 재개할 수 있다. |
| **턴** | Run 안에서 LLM을 한 번 호출하는 것. 한 턴에 여러 도구를 동시에 호출할 수 있다. |
| **도구 호출** | LLM이 요청하고 서버가 검증한 뒤 실행하는 동작. |

Run을 시작하는 이벤트(트리거):

| 트리거 | 언제 | 상태 |
|---|---|---|
| `goal_submitted` | 사용자가 목표를 입력 | 구현됨 |
| `email_received` | 업무 스레드에 메일 도착 (현재는 시뮬레이터) | 구현됨 |
| `manual_retry` | 사용자가 재시도 | 구현됨 |
| `goal_updated` | 사용자가 목표를 수정 | 구현됨 |
| `thread_reply` | Gmail 업무 스레드에 상대 재답장 | Gmail 설계 |
| `reply_requested` | 사용자가 답장 초안 요청 | Gmail 설계 |

## 1.3 계층 구조

```
┌ 화면 (React, frontend/src) ─────────────────────────────────────────────┐
│ 대시보드 · 업무 상세 · 승인 카드 · 타임라인 · 토큰 사용량 · 워크스페이스      │
└───────────── REST (쿠키 인증, CSRF 헤더) ─────── SSE (업무 상세 실시간) ──┘
┌ API (backend/app/api) ──────────────────────────────────────────────────┐
│ auth · tasks(생성·조회·재시도·취소·목표 수정·완료·승인) · demo · events     │
│ 모든 조회에 user_id 조건, 남의 데이터는 404                                │
└──────────────────────────────┬──────────────────────────────────────────┘
┌ 오케스트레이터 (backend/app/agent/orchestrator.py) ─────────────────────┐
│ Run 생성 · 업무별 잠금 · 백그라운드 스레드 실행                             │
│ 루프: 실행 전 확인 → LLM 턴 → 도구 게이트 → 결과를 붙여 다음 턴             │
│ 한도: 10단계 · 420초 · 일시 오류 2회 재시도 · 승인 시 일시정지              │
└──────┬──────────────────────┬──────────────────────────┬────────────────┘
┌ LLM (agent/llm.py,        ┌ 도구 (agent/tools.py)      ┌ 보안 가드 (agent/guard.py)
│  gemini_llm.py)          │ 허용 목록 10개            │ 주입 탐지 · 외부 데이터 격리
│ 공급자 중립 메시지 형식   │ Pydantic 입력 검증         │ 다른 고객 연락처 유출 차단
│ Gemini / Claude 교체      │ 서버가 user·task 주입     │
│ 사용량 정규화             │ 승인 필요 도구 분리        │
└──────────────────────────┴───────────┬──────────────┴──────────────────
                                ┌ DB (models.py, Alembic) ┐
                                │ users · tasks · emails  │
                                │ customers · documents   │
                                │ agent_runs · approvals  │
                                │ agent_action_logs       │
                                └─────────────────────────┘
```

## 1.4 Run 하나의 흐름

1. 이벤트가 오면 `start_run`이 업무별 잠금 안에서 활성 Run이 없는지 확인하고 Run을 만든다.
2. 첫 메시지에 `<user_goal>`, DB에서 복원한 `<task_state>`, 최근 행동 이력 25건을 넣는다.
3. 루프를 돈다.
   - **실행 전 확인:** Run이 아직 RUNNING인지(사용자 취소 여부), 단계 한도와 시간 한도를 넘지 않았는지.
   - **LLM 턴:** 시스템 프롬프트, 도구 정의, 대화 기록을 보낸다. 일시 오류면 3초, 8초 뒤 재시도한다.
   - **응답 직후 확인:** LLM이 생각하는 동안 취소됐으면 이 턴을 버린다.
   - **도구 게이트:** 허용 목록, 입력 검증, 소유권 검사. 실패하면 오류를 결과로 돌려준다.
   - **승인 필요 도구:** 실행하지 않고 승인 요청을 만든 뒤 Run을 멈춘다.
   - **상태 확정:** 오류 없이 업무 상태가 정해지면 Run을 끝낸다.
4. 승인되면 도구를 실행하고 결과를 붙여 같은 Run을 재개한다. 승인은 체크포인트라 단계 수가 초기화된다.
5. 대기 상태로 끝나면 LLM은 호출되지 않는다. 다음 이벤트가 새 Run을 시작한다.

## 1.5 도구

| 도구 | 권한 | 하는 일 |
|---|---|---|
| `plan_goal` | 현재 업무 쓰기 | 목표를 하위 목표 2~7개로 나눔 |
| `search_customer` | 읽기 | 내 고객 검색 |
| `search_document` | 읽기 | 내 문서 키워드 검색. **2부에서 RAG 검색으로 교체** |
| `draft_email` | 생성 | 초안 저장. 수신 주소는 서버가 결정 |
| `send_email` | 승인 필요 | 승인된 초안만 발송 |
| `check_email` | 읽기 | 이 업무의 새 메일 확인 |
| `analyze_email` | 읽기 | 구조화 분석. 의심 지시문 분리 |
| `create_followup_task` | 쓰기 | 후속 업무 생성 (업무당 5개) |
| `complete_plan_step` | 현재 업무 쓰기 | 하위 목표 완료 |
| `update_task_status` | 현재 업무 쓰기 | 상태 확정. 완료는 서버 조건 통과 시만 |

LLM은 `user_id`, `task_id`를 넘길 수 없다. 입력 스키마에 없고 추가 필드는 거부된다.

## 1.6 업무 상태

| 상태 | 의미 |
|---|---|
| 시작 전 `PENDING` | 아직 손대지 않음, 사용자가 처리할 후속 업무, (Gmail 설계) 참고용 메일 |
| 진행 중 `IN_PROGRESS` | Agent 실행 중 |
| 대기 중 `WAITING` | 외부 이벤트 대기. LLM 호출 없음 |
| 조치 필요 `ACTION_REQUIRED` | 승인 대기 또는 사용자 결정 필요 |
| 중단됨 `BLOCKED` | 한도 초과나 오류. 재시도로 이어감 |
| 완료 `COMPLETED` | 서버 조건을 통과한 종료 |
| 취소됨 `CANCELLED` | 사용자가 닫음. 기록만 남음 |

## 1.7 안전장치

- **격리:** 모든 조회와 도구에 사용자 조건. 남의 ID는 존재 여부도 알려주지 않는다.
- **승인:** 외부로 나가는 동작은 사용자 승인 전에는 실행되지 않는다. 승인 시 내용을 고칠 수 있고 원문은 로그에 남는다.
- **완료 조건:** 하위 목표가 남아 있거나 승인 대기가 있으면 완료를 거부한다.
- **주입 방어:** 외부 내용은 `<untrusted_external_content>`로 감싸고 정규식으로 탐지한다. 시스템 프롬프트가 외부 지시를 따르지 말라고 못 박는다.
- **폭주 방지:** 단계, 시간, 재시도 횟수 한도.
- **인증과 웹 보안:** bcrypt, HttpOnly 쿠키, CSRF 헤더와 출처 검사, 보안 헤더, 속도 제한.
- **기록:** 모든 행동을 이유, 입력, 결과, 위험도와 함께 타임라인에 남긴다. 턴별 토큰 사용량도 저장한다.

## 1.8 실제와 가상, 그리고 바뀔 부분

| 구성 | 지금 | Gmail 설계 반영 후 |
|---|---|---|
| Agent 판단 | 실제 LLM | 같음 |
| 업무의 출발점 | 사용자가 목표 입력 | 받은편지함의 업무 메일 (목표 입력은 보조) |
| 고객 · 문서 | 가입 시 생성되는 가상 데이터 | 메일 상대는 `contacts`로 자동 저장, 가상 데이터는 데모 모드만 |
| 메일 발송 | DB 기록만 변경 | Gmail로 실제 스레드 답장 |
| 고객 답변 | 시뮬레이터 버튼 | 90초 주기 Gmail 확인 |
| 기한 · 알림 | 없음 | 캘린더 일정과 팝업 알림, 앱 안 D-day |
| 접수 처리 | Agent 루프 | 고정 파이프라인 (판별 1회 + 분석 1회) |
| 답장 맥락 | 등록 고객 기준 | 해당 스레드만 |

## 1.9 RAG가 들어갈 자리

> → 1단계에서 바뀜: 메일 업무의 답장 초안은 코드가 먼저 검색해 프롬프트에 넣는다(Agent 도구 아님). [RAG 1단계 설계](2026-10-29-rag-documents-design.md) 5절.

RAG는 새 계층 하나로 들어간다. Agent 루프와 도구 게이트는 바꾸지 않고, 검색 결과를 넣는 입구 두 곳만 추가한다.

```
                       ┌──────── 지식 계층 (2부) ────────┐
 문서 업로드 ─┐        │ 색인 작업 큐 → 텍스트 추출 → 덩어리 │
 Gmail 메일 ──┼──────▶ │ → 주입 검사 → 임베딩 → 저장       │
 완료 업무 ───┘        │ 검색기: 범위 필터 + 의미 + 키워드  │
                       └───────┬───────────────┬────────┘
                    입구 ①     │               │   입구 ②
          접수 파이프라인이     │               │   Agent 도구
          분석 전에 자동 검색 ◀─┘               └─▶ search_knowledge
                                                    (답장 작성 · 재답장 판단)
```

# 2부. RAG 설계

## 2.1 목적

Agent는 지금 보고 있는 메일 밖의 사실을 모른다. 답장을 쓸 때 해당 스레드만 보도록 일부러 막아 두었기 때문이다.
그래서 단가, 리드타임, 결제 조건 같은 숫자를 지어낼 위험이 있고, 상대와의 지난 맥락이나 내 말투도 반영하지 못한다.

RAG의 목표는 세 가지다.

1. 답장과 분석에 **내 자료의 정확한 사실**을 넣는다.
2. **같은 상대와의 지난 대화와 비슷한 지난 업무**를 참고하게 한다.
3. 어떤 자료를 참고했는지 **출처를 보여줘** 사용자가 바로 확인하게 한다.

### 범위 밖

- 이미지 · 스캔 PDF의 글자 인식
- 웹 검색
- 사용자 간 지식 공유
- 모델 미세조정

## 2.2 지식 출처

| 출처 | 가져오는 시점 | 쓰임 | 기본 공유 등급 |
|---|---|---|---|
| **문서** (단가표, 사양서, 정책, 견적 양식) | 사용자가 업로드 | 답장 속 사실 | 업로드 시 선택 |
| **업무 요약** (완료한 업무의 요약, 할 일, 처리 메모) | 업무 완료 시 | 비슷한 업무의 할 일 제안 | 내부 |
| **메일** (업무로 판정된 받은 메일, 내가 보낸 메일) | Gmail 동기화 + 과거 백필 | 상대와의 맥락 | 상대 한정 |
| **문체 예시** (사용자가 고른 내 메일) | 사용자가 지정 | 말투 | 문체 전용 |

색인하지 않는 것: 업무 아님 · 필터링된 메일, 주입 의심 판정을 받은 덩어리, 사용자가 색인 제외한 스레드.

### 공유 등급

검색 결과가 밖으로 나가는 답장에 쓰일 수 있는지를 정하는 값이다. 2.7절의 범위 규칙이 이 값을 쓴다.

| 등급 | 의미 |
|---|---|
| `shareable` | 어떤 상대에게 보내는 답장에도 인용 가능 (공개 단가표, 제품 사양) |
| `internal` | 분석과 할 일 제안에만 사용, 답장에는 불가 (내부 원가, 메모) |
| `counterpart` | 같은 상대 · 같은 도메인과의 답장에만 사용 (그 상대와의 메일, 상대 전용 견적) |
| `style` | 말투 참고만. 사실 근거로 쓰지 않음 |

## 2.3 수집과 덩어리 나누기

### 문서

- 지원 형식: PDF(텍스트 레이어), DOCX, TXT, MD, CSV.
- 텍스트 추출: `pypdf`, `python-docx`. 표는 행 단위로 `열이름: 값` 형식의 텍스트로 바꾼다.
- 나누기: 제목 단위로 먼저 자르고, 800자를 넘으면 문단 경계에서 다시 자른다. 앞 덩어리 끝 100자를 겹친다.
- 표는 행이 잘리지 않게 20행 단위로 묶고, 덩어리마다 표 머리글을 다시 붙인다.
- 파일 원본은 DB에 저장하지 않는다. 추출한 텍스트와 파일 이름, 크기, 해시만 남긴다. 최대 10MB.

### 메일

- 인용, 전달 본문, 서명을 뺀 본문을 메일 한 통 = 덩어리 하나로 저장한다. 1,500자를 넘으면 문단 경계에서 자른다.
- 덩어리 앞에 `보낸 사람 · 날짜 · 제목` 머리글을 붙여 임베딩한다.
- **과거 백필:** Gmail 연결 시 업무 카드용 3일과 별개로, 색인용으로 `RAG_MAIL_BACKFILL_DAYS`(기본 180일)를 가져온다.
  판별을 거쳐 업무 메일만 색인하고, 한도 안에서 며칠에 걸쳐 나눠 처리한다.

### 업무 요약

- 업무가 완료되면 `제목 · 한 줄 요약 · 상대가 원하는 것 · 할 일과 처리 메모 · 결과`를 덩어리 하나로 만든다.
- 다시 열렸다가 완료되면 갱신한다.

### 공통

- 덩어리마다 내용 해시를 저장해 같은 내용은 다시 임베딩하지 않는다.
- 색인 전에 `guard.detect_injection`을 돌린다. 걸린 덩어리는 `flagged`로 저장만 하고 검색에서 제외하며, 자료실 화면에 표시한다.

## 2.4 임베딩

> → 1단계에서 바뀜: 1단계는 임베딩 없이 키워드 검색만 한다. 다음 단계에서 측정 결과를 보고 정한다.

| 항목 | 결정 |
|---|---|
| 모델 | `gemini-embedding-2` (Gemini API의 현재 권장 임베딩 모델, 100개 이상 언어 지원) |
| 차원 | 768 (지원 범위 128~3072 중 권장값. 개인 규모에서 저장 공간과 속도의 균형) |
| 입력 한도 | 8,192토큰. 덩어리 크기는 이보다 훨씬 작게 유지 |
| 작업 구분 | 이 모델은 `task_type` 인자를 받지 않는다. 문서는 `title: {제목} \| text: {본문}`, 질의는 `task: search result \| query: {질의}` 접두어를 붙인다 |
| 배치 | 색인은 배치 API 사용 (기본 가격의 50%) |
| 기록 | 덩어리마다 모델 이름과 차원을 저장. 모델을 바꾸면 해당 덩어리만 다시 만든다 |

임베딩 호출은 `Embedder` 인터페이스 뒤에 둔다. 테스트에서는 텍스트 해시로 결정적인 벡터를 만드는 가짜 임베더를 쓴다.

### 비용과 데이터 정책

- 가격: 텍스트 입력 100만 토큰당 0.20달러, 배치 0.10달러. 무료 등급은 무료.
- 예상: 메일 5,000통 × 평균 500토큰 = 250만 토큰. 배치 기준 약 0.25달러로 개인 규모에서는 비용이 거의 들지 않는다.
- **무료 등급은 입력이 Google 제품 개선에 사용된다** (가격 페이지의 "Used to improve our products" 항목이 무료 Yes, 유료 No).
  실제 업무 메일과 문서를 색인할 때는 **유료 등급 키를 쓰도록** 하고, 무료 키로 실제 메일을 색인하려 하면 설정 화면에서 경고한다.
  이 경고는 분석용 LLM 호출에도 똑같이 해당한다.

## 2.5 저장

### 새 테이블

**`knowledge_sources`** — 출처 단위 (문서 파일 하나, 메일 한 통, 업무 하나)

| 컬럼 | 설명 |
|---|---|
| `user_id` | 소유자 |
| `kind` | `document` / `email` / `task_summary` / `style` |
| `ref_id` | 원본 행 번호 (documents, emails, tasks) |
| `title`, `visibility` | 표시 이름, 공유 등급 |
| `counterpart_email`, `counterpart_domain` | 메일 · 업무의 상대 |
| `thread_id` | Gmail 스레드 |
| `occurred_at` | 메일 날짜, 문서 업로드일, 업무 완료일 |
| `status` | `queued` / `indexed` / `flagged` / `failed` / `excluded` |
| `error` | 실패 이유 |

**`knowledge_chunks`** — 덩어리 단위

| 컬럼 | 설명 |
|---|---|
| `source_id`, `user_id` | 출처와 소유자 (검색 필터용으로 중복 저장) |
| `ordinal` | 출처 안 순서 |
| `text` | 덩어리 본문 |
| `content_hash` | 중복 방지 |
| `embedding` | PostgreSQL: `vector(768)` / SQLite: 바이트 배열 |
| `embedding_model` | 예: `gemini-embedding-2@768` |
| `flagged` | 주입 의심 |

**`index_jobs`** — 색인 작업 큐 (`source_id`, `attempts`, `next_run_at`, `last_error`)

### 데이터베이스별 처리

- **운영 PostgreSQL:** pgvector 확장. Alembic 마이그레이션에서 `CREATE EXTENSION IF NOT EXISTS vector`와 `pg_trgm`을 실행한다.
  벡터에는 HNSW 색인(코사인), 본문에는 trigram GIN 색인을 둔다.
  Railway 기본 PostgreSQL 대신 pgvector가 들어 있는 템플릿으로 DB를 만들어야 한다. 이 템플릿들도 확장은 기본으로 꺼져 있어 위 명령이 필요하다.
- **로컬 SQLite:** 벡터를 바이트로 저장하고 파이썬에서 코사인 유사도를 직접 계산한다. 사용자 필터로 먼저 거르므로 수천 건 규모에서는 충분하다.
  키워드 검색은 `LIKE`와 글자 조각 일치 점수로 대신한다.
- 두 경로는 `KnowledgeStore` 인터페이스 하나로 감춘다.

### 삭제

- 문서 · 메일 · 업무를 지우면 해당 출처와 덩어리를 함께 지운다.
- Google 연결을 해제하며 "메일 본문 삭제"를 고르면 메일 출처의 덩어리도 모두 지운다.
- 벡터만 남아 지운 내용을 검색으로 되찾는 일이 없게 한다.

## 2.6 검색

> → 1단계에서 바뀜: 1단계는 임베딩 없이 키워드 검색만 한다. 다음 단계에서 측정 결과를 보고 정한다.

`KnowledgeRetriever.search(user, query, scope, k=5)`

1. **범위 필터:** 사용자 조건은 서버가 항상 넣는다. 그다음 2.7절의 범위 규칙으로 허용된 공유 등급과 상대만 남긴다. `flagged`는 제외한다.
2. **의미 검색:** 질의 임베딩으로 상위 30개.
3. **키워드 검색:** trigram 유사도로 상위 30개. 견적 번호, 제품 코드처럼 의미 검색이 놓치는 것을 잡는다.
4. **순위 합치기:** 두 목록을 RRF(순위 역수 합)로 합친다.
5. **가산점:** 같은 상대 ×1.5, 같은 도메인 ×1.2, 오래된 메일은 1년에 걸쳐 완만히 감쇠. 문서는 감쇠하지 않는다.
6. **정리:** 같은 출처의 덩어리는 최대 2개, 점수가 기준 미만이면 버린다. 아무것도 없으면 빈 결과를 돌려준다.
7. **결과 형식:** 덩어리마다 `chunk_id`, 출처 제목, 종류, 날짜, 공유 등급, 본문을 주고, 본문은 `<untrusted_external_content>`로 감싼다.

질의 임베딩 결과는 같은 Run 안에서 재사용한다.

## 2.7 범위 규칙 (유출 방지의 핵심)

Gmail 설계에서 답장 맥락을 스레드 하나로 막았던 이유는 다른 상대의 정보가 섞여 나가는 것을 막기 위해서였다.
RAG는 이 벽을 다시 여는 장치이므로, **용도별로 허용 범위를 서버가 정한다.** Agent는 범위를 지정할 수 없다.

| 용도 (scope) | 허용 | 쓰는 곳 |
|---|---|---|
| `intake` | `shareable` · `internal` 문서 전부, 같은 상대의 `counterpart` 자료와 메일, 모든 업무 요약 | 접수 파이프라인의 분석 |
| `thread_reply` | `intake`와 같음 | 재답장 판단 |
| `reply` | `shareable` 문서, 같은 상대 · 같은 도메인의 `counterpart` 자료, `style` | 답장 작성 |

- `internal` 자료와 다른 상대의 메일은 **답장 작성 범위에 절대 들어가지 않는다.**
- 업무 요약은 다른 상대의 업무도 포함할 수 있으므로 `reply`에서 제외한다. 할 일 제안에만 쓴다.
- `style` 자료는 결과에 "말투 참고, 사실로 인용 금지" 표시를 붙여 넘긴다.

## 2.8 Agent 연결

> → 1단계에서 바뀜: 메일 업무의 답장 초안은 코드가 먼저 검색해 프롬프트에 넣는다(Agent 도구 아님). [RAG 1단계 설계](2026-10-29-rag-documents-design.md) 5절.

### 입구 ① 접수 파이프라인 (자동, LLM 호출 수 증가 없음)

분석 호출 직전에 코드가 `scope=intake`로 두 번 검색한다.

- 질의 A: 메일 제목 + 본문 앞 500자 → 관련 문서와 비슷한 지난 업무 상위 3개
- 질의 B: 같은 상대 필터만 걸고 최신순 → 그 상대와의 지난 업무 요약 2개

결과를 분석 프롬프트의 `<related_knowledge>` 블록에 넣는다. 분석 결과에는 참고한 `chunk_id` 목록을 추가로 받아 업무에 저장한다.

### 입구 ② Agent 도구

| 도구 | 권한 | 하는 일 |
|---|---|---|
| `search_knowledge(query, kind?)` | 읽기 | 현재 트리거의 범위로 검색. `kind`로 문서 · 메일 · 업무 요약 · 문체를 고를 수 있으나 범위 밖은 결과에서 빠진다 |

- 기존 `search_document`는 `search_knowledge(kind="document")`로 대체한다. 데모 모드의 가상 문서도 같은 경로로 색인한다.
- `draft_reply`에 `sources: chunk_id[]` 인자를 추가한다. 서버는 각 출처가 `reply` 범위 안인지 다시 검사하고, 범위 밖이면 초안 작성을 거부한다.
- 시스템 프롬프트에 규칙을 추가한다.
  - 숫자, 날짜, 조건은 검색 결과에 있을 때만 쓰고 출처를 `sources`에 넣는다.
  - 검색 결과에 없으면 "확인 후 회신드리겠습니다"처럼 쓰고 사용자에게 할 일로 남긴다.

### 출처 표시

- **승인 카드:** 초안 아래 "참고한 자료" 목록. 제목, 종류, 날짜, 공유 등급, 인용된 문장 미리보기.
- **유출 경고 확장:** 초안의 숫자나 고유명사가 범위 밖 덩어리에만 있고 허용된 출처에는 없으면 경고한다. 사람이 마지막에 본다는 전제의 보조 장치다.
- **업무 상세:** "관련 지난 업무" 영역에 입구 ①이 찾은 업무 요약을 링크로 보여준다.

## 2.9 화면

- **자료실 (새 페이지):** 문서 업로드(끌어다 놓기), 목록, 공유 등급 변경, 색인 상태(대기 · 완료 · 의심 · 실패), 삭제, 다시 색인.
- **설정:** 메일 색인 사용 여부, 백필 기간, 색인 진행률, 유료 키 여부 경고, 전체 색인 삭제.
- **업무 상세:** 관련 지난 업무, 스레드 단위 "이 스레드 색인 제외".
- **승인 카드:** 참고한 자료, 유출 경고.

## 2.10 색인 작업 처리

- 새 출처는 `index_jobs`에 넣고, 백그라운드 색인 스레드가 처리한다. 메일 동기화 스레드와 같은 임대 방식으로 중복 처리를 막는다.
- 임베딩은 최대 100개씩 묶어 호출한다. 백필처럼 양이 많으면 배치 API로 보낸다.
- 429와 5xx는 지수 대기 후 재시도, 5회 실패하면 `failed`로 두고 자료실에 표시한다.
- 임베딩 호출의 토큰 사용량도 기존 사용량 기록처럼 저장해 설정 화면에 보여준다.

## 2.11 보안 요약

| 위험 | 대응 |
|---|---|
| 다른 사용자 데이터 검색 | SQL 단계에서 사용자 조건 고정. Agent가 넘길 수 없음 |
| 다른 상대 정보가 답장에 섞임 | 용도별 범위 규칙, `sources` 서버 재검사, 승인 카드 경고 |
| 과거 메일 속 지시문이 나중에 되살아남 | 색인 전 주입 검사로 제외, 검색 결과도 외부 데이터 태그로 감쌈 |
| 지운 내용이 벡터로 남음 | 출처 삭제 시 덩어리 함께 삭제 |
| 실제 메일이 학습 데이터로 쓰임 | 실제 데이터 색인은 유료 등급 키 사용, 무료 키면 경고 |
| 로그에 본문 누적 | 검색 도구 로그에는 `chunk_id`, 출처 제목, 점수만 남김 |

## 2.12 평가

- **오프라인 테스트 (가짜 임베더):** 덩어리 나누기 경계, 범위 규칙(특히 `reply`에서 `internal`과 다른 상대 제외), 삭제 연쇄, 주입 덩어리 제외, `sources` 재검사.
- **검색 품질 평가 (opt-in, 실제 임베딩):** 본인 자료로 질문 20~30개와 정답 출처를 만든다.
  상위 5개 안에 정답 출처가 들어오는 비율(recall@5)과 정답의 평균 순위 역수(MRR)를 잰다.
  덩어리 크기, 가산점, 키워드 비중을 바꿀 때마다 이 수치로 비교한다.
- **답장 점검:** 실제 메일로 답장 초안을 만들어 숫자마다 출처가 붙는지, 출처 없는 숫자가 없는지 확인한다.
- **로컬 브라우저 점검:** 각 단계 완료 시 자료실 업로드부터 승인 카드 출처 표시까지 화면에서 직접 확인한다.

## 2.13 구현 단계

| 단계 | 내용 | 시작 조건 |
|---|---|---|
| **R1 기반 + 문서** | 테이블, `Embedder` · `KnowledgeStore` · `KnowledgeRetriever`, 가짜 임베더, 문서 업로드와 색인, `search_knowledge` 도구로 `search_document` 대체, 자료실 화면 | 지금 가능 (데모 문서로 검증) |
| **R2 업무 요약** | 완료 업무 요약 색인, 접수 시 관련 지난 업무, 업무 상세 표시 | 지금 가능 |
| **R3 메일 색인** | 업무 메일과 보낸 메일 색인, 과거 백필, 삭제 연쇄, 스레드 제외 | Gmail 설계 2~3단계 이후 |
| **R4 답장 범위와 출처** | `reply` 범위, `draft_reply.sources`, 승인 카드 출처와 경고, 프롬프트 규칙 | Gmail 설계 6단계와 함께 |
| **R5 문체** | 문체 예시 지정, 답장 작성 시 말투 참고 | R4 이후 |

→ 1단계에서 바뀜: 순서는 R1+R4(문서 → 답장, 키워드 검색) → R2 → R3 → R5. R1+R4는 2026-10-30 완료.

R1과 R2는 Gmail 연동과 독립적이라 먼저 진행할 수 있다. 다만 실제 데이터가 없으면 검색 품질 평가는 할 수 없으므로, R1 · R2 단계의 목표는 **구조와 안전 규칙 검증**이다.

## 2.14 결정이 필요한 것

1. **메일 백필 기간:** 기본 180일을 제안한다. 길수록 맥락이 풍부하지만 색인 시간과 저장 공간이 는다.
2. **유료 키 사용:** 실제 메일 색인 전에 Gemini 유료 등급 키로 바꿀지. 바꾸지 않으면 실제 메일 색인을 막을지, 경고만 할지.
3. **문서 공유 등급 기본값:** 업로드 시 기본값을 `internal`(안전)로 둘지 `shareable`(편리)로 둘지. 이 문서는 `internal`을 제안한다.
4. **진행 순서:** R1 · R2를 Gmail 연동보다 먼저 할지, Gmail 연동 1~3단계를 먼저 할지.

→ 1단계에서 바뀜 (2026-10-29 사용자 결정): 4번은 해결됨(Gmail 6단계 뒤 RAG). 3번은 `internal`로 확정. 2번은 임베딩을 붙이는 단계로 미룬다. 1번은 메일 색인(R3)에서 정한다.
