# 받은 업무 화면 설계 (Gmail 설계 5단계)

- 작성일: 2026-10-26
- 상태: 사용자 검토 대기
- 상위 설계: `docs/superpowers/specs/2026-10-10-gmail-calendar-design.md` (5절 화면, 12.2절 합치기)
- 앞 단계: 1~4단계 완료. 메일 동기화, 업무 메일 판별 · 접수, 캘린더 일정이 `main`에 있다.

## 1. 목적

지금은 메일에서 업무가 만들어져도 기존 대시보드에 섞여 보이고, 요약 · 기한 · 할 일을 다룰 화면이 없다.
이번 단계의 목표는 **앱을 열면 오늘 처리할 업무가 중요한 순서로 보이고, 업무 하나를 열면 무엇을 해야 하는지와 마감이 한눈에 보이는 것**이다.

사용자가 정한 원칙:
- 첫 화면에서 가장 먼저 눈에 들어와야 할 것은 **처리할 업무를 중요도와 급한 정도로 나눈 목록**이다.
- **놓치지 않기:** 스누즈와 답장 넛지를 함께 넣는다.
- 같은 상대가 새 메일로 보낸 수정 요청은 **물어보고 사람이 합친다.**

### 목표
- 받은 업무 첫 화면: 묶음별 정렬, 중요도 신호등, 기한 배지, 할 일 진행도
- 업무 상세: 요약 카드, 기한 수정 · 확인, 중요도 변경, 할 일 편집, 닫기 · 취소 · 스누즈
- 스누즈, "내가 답장 안 한 업무" 넛지, 업무 합치기, 업무로 처리, 다시 분석
- 앱 안 알림(브라우저 알림)과 탭 제목 건수

### 하지 않는 것 (6단계 이후)
- 답장 초안 작성 · 발송, Gmail에서 직접 보낸 답장 감지
- "상대 답장 없음" 넛지 연결. 이번에는 화면 자리와 상태값만 준비한다.
- 재답장으로 업무 내용 갱신 (상위 설계 12.1절)
- 목표 입력 기능을 보조 메뉴로 정리하는 일 (7단계)

### 실패로 보는 경우
- 스누즈해 둔 업무가 숨겨진 사이에 마감을 놓치는 것
- 잘못 합친 업무를 되돌릴 수 없는 것
- 알림이 반복되어 같은 업무로 여러 번 울리는 것
- 지금 처리 목록이 너무 길어져서 "지금"이라는 의미가 없어지는 것

## 2. 첫 화면: 받은 업무

경로 `/`. 기존 대시보드는 `/tasks`("전체 업무" 메뉴)로 옮긴다. 기능은 그대로다.

### 2.1 화면 구성 (위에서 아래로)

1. **상태 줄:** Gmail 연결 상태, 마지막 확인 시각, "지금 확인" 버튼. 재연결이 필요하면 기존 빨간 배너가 뜬다.
2. **요약:** 크게 "지금 처리 N건", 옆에 작게 "이번 주 N건 · 나중에 N건". 오른쪽 위에 중요도 범례 한 줄(● 높음 ◐ 보통 ○ 낮음).
3. **탭**

   | 탭 | 들어가는 업무 |
   |---|---|
   | 처리할 일 | `ACTION_REQUIRED` · `IN_PROGRESS` · `BLOCKED`, 그리고 분석 대기(`PENDING` + `brief.analysis` 가 `pending` 또는 `failed`) |
   | 답장 보냄 | `WAITING` |
   | 참고용 | `PENDING` + `brief.analysis == "done"` |
   | 완료 | `COMPLETED`, `CANCELLED`, 합쳐진 업무 제외 |

   대상은 메일 업무(`origin="mail"`)뿐이다. 합쳐진 업무(`merged_into_id`가 있음)는 어느 탭에도 나오지 않는다.
4. **처리할 일 탭 안의 묶음:** 지금 처리 → 이번 주 → 나중에 (2.2절). 묶음 사이에 작은 제목을 둔다.
5. **맨 아래 접힌 영역 2개**
   - "나중에 보기 N건": 스누즈 중인 업무. 펼치면 언제 다시 뜨는지 보인다.
   - "업무 아님으로 분류된 메일 N건": 펼치면 보낸 사람, 제목, 판별 이유, **"업무로 처리"** 버튼. 최근 30일, 최대 50건.

### 2.2 묶음 기준

기준 시각은 지금, 날짜는 사용자 시간대(`USER_TIMEZONE`)로 계산한다. "오늘 · 내일"은 달력 날짜 기준이다.

| 묶음 | 조건 (위에서부터 먼저 맞는 것) |
|---|---|
| **지금 처리** | 기한이 지났거나 오늘 · 내일이다. 또는 중요도가 높음이고 기한이 3일 안이다. |
| **이번 주** | 기한이 7일 안이다. 또는 기한이 없고 중요도가 높음이다. |
| **나중에** | 나머지 |

- 분석 대기 업무는 기한을 모르므로 "나중에" 맨 위에 두고 "분석 중"으로 표시한다.
- **묶음 안 정렬:** 중요도(높음 → 보통 → 낮음) → 기한(이른 순, 기한 없음은 마지막) → 받은 순서(오래된 순).
- 묶음 판정은 서버가 해서 내려준다. 화면과 알림이 같은 기준을 쓰게 하기 위해서다.

### 2.3 업무 카드

- **왼쪽 중요도 점:** 높음 ● 꽉 찬 빨강, 보통 ◐ 반쯤 찬 노랑, 낮음 ○ 빈 초록.
  - 글자는 쓰지 않는다. 마우스를 올리면 "중요도 높음" 같은 설명이 뜨고, 화면 낭독기도 같은 글자를 읽는다.
  - 흑백에서도 모양으로 구분된다.
- **본문:** 보낸 사람(이름 · 소속), 한 줄 요약(굵게), 할 일 진행도("할 일 1/3", 할 일이 없으면 생략)
- **오른쪽 기한 배지:** 테두리만 있는 글자 배지
  - 예: "D+1 지남", "오늘", "D-1 내일", "D-5", "기한 없음"
  - 지난 기한만 빨간색으로 강조한다.
  - 추정 기한이면 " · 확인 필요"를 붙인다.
- **상황 표시** (해당할 때만): "2일째 답장 안 함"(넛지), "다시 표시됨"(스누즈에서 막 돌아옴, 24시간), "합치기 제안"(합칠 후보가 있음)
- 카드를 누르면 업무 상세로 간다.

## 3. 업무 상세

경로는 기존 `/tasks/{id}`를 쓴다. 메일 업무일 때 아래 구성을 보여주고, 다른 업무는 지금 화면 그대로 둔다.

### 3.1 맨 위 안내 띠 (해당할 때만, 여러 개면 위에서부터)
1. **분석 실패:** "자동 분석에 실패했습니다" + **"다시 분석"** 버튼
2. **합치기 제안:** 4.3절
3. **답장 넛지:** "2일째 답장하지 않았습니다" (4.2절)
4. **상대 답장 없음 (6단계에서 연결):** "상대 답장 없음 — 다시 연락할까요?" + 다시 연락하기 / 완료로 닫기. 이번 단계에서는 화면 부품만 만들고 띄우지 않는다.

### 3.2 요약 카드
- 한 줄 요약, 보낸 사람, 받은 날짜, **상대가 원하는 것** 목록
- **중요도 신호등:** 세 점 중 하나를 눌러 바꾼다. 이 곳에서만 "높음 / 보통 / 낮음" 글자를 함께 보여준다.
- **기한 영역**
  - 기한, 남은 기간(D-day), 기한 근거 문장, "캘린더에서 열기"(기존), 캘린더 상태 줄(기존)
  - **기한 수정:** 날짜와 선택적 시각을 고른다. 기한 없애기도 가능하다. 저장하면 확정 기한(`explicit`)이 되고 캘린더를 다시 반영한다.
  - 추정 기한이면 "확인 필요" 표시와 **"이 기한이 맞아요"** 버튼. 누르면 확정 기한이 되고 캘린더 제목의 "(확인 필요)"가 빠진다.
  - 기한이 없으면 "기한 추가" 버튼만 보인다.

### 3.3 할 일 체크리스트
- 항목별: 체크박스, 제목, 항목 기한(있으면), 처리 메모(펼쳐서 입력), 삭제
- 맨 아래: 할 일 추가 입력
- **체크한 할 일**은 `evidence`에 메모를, `done=true`를 저장한다.
- **사용자가 추가한 항목**은 `source="user"`로 둔다.
- 삭제한 항목은 목록에서 바로 지운다. 확인 단계는 카드 안에서 "삭제 → 되돌리기"로 처리한다.
- 바뀌면 캘린더 일정 설명의 할 일 체크 표시도 다시 반영한다.
- 할 일을 다 끝내면 "답장 초안 만들기"를 강조한다(6단계 전까지는 비활성 상태로 강조만).

### 3.4 버튼
- **나중에 보기(스누즈):** 4.1절
- **답장 필요 없음으로 닫기:** 이유 입력(선택) 후 `COMPLETED`. 타임라인에 이유를 남기고 캘린더에 ✓를 붙인다.
- **업무 취소:** 기존 기능
- **답장 초안 만들기:** 6단계 전까지 비활성 상태로 "6단계에서 제공" 안내

### 3.5 그 아래
원본 메일 스레드(접힘), 오른쪽 타임라인, 토큰 사용량은 지금과 같다.

## 4. 새 동작

### 4.1 스누즈 (나중에 보기)
- **시간 선택지:** 오늘 오후 6시(이미 지났으면 숨김), 내일 오전 9시, 다음 주 월요일 오전 9시, 직접 선택(날짜 + 시각). 모두 사용자 시간대 기준이다.
- **스누즈 중에는** "처리할 일" 묶음에서 빠지고, 맨 아래 "나중에 보기"에 들어간다. 업무 상태와 캘린더는 바꾸지 않는다.
- **다시 나타나는 때** (먼저 오는 것)
  1. 정한 시각
  2. 같은 스레드에 **상대 메일이 새로 도착**했을 때(합쳐진 스레드 포함)
  3. **기한 하루 전 오전 9시.** 기한이 스누즈 시각보다 먼저 오는 경우의 안전장치다.
  4. 사용자가 "나중에 보기" 목록에서 **"지금 보기"**를 눌렀을 때
- **다시 나타나면** 카드에 "다시 표시됨"을 24시간 붙이고, 앱이 열려 있으면 브라우저 알림을 한 번 띄운다.
- **(참고)** 아래 "업무로 처리"로 기존 업무에 메일이 붙는 경우도 새 메일 도착과 같이 스누즈를 지운다.
- **해제 방식:** 해제 처리는 따로 돌리지 않는다. 목록을 그릴 때와 알림을 확인할 때 서버가 계산한다. 다만 새 메일 도착 시(2번)에는 접수 단계에서 바로 스누즈를 지운다.
- 업무가 완료 · 취소되면 스누즈는 의미가 없어지므로 지운다.

### 4.2 답장 넛지
- **내가 답장 안 한 업무 (이번 단계)**
  - 조건: 메일 업무이고, 분석 결과 `needs_reply=true`이고, 상태가 처리할 일이다. 그리고 **이 업무의 가장 최근 상대 메일**(합쳐진 스레드 포함)을 받은 지 **2일**(48시간)이 지났고, 스누즈 중이 아니다.
  - 상대 메일이 새로 오면 날짜를 다시 셉니다. 알림 키에 그 메일 번호를 넣어서, 새 메일마다 한 번씩 알린다. (내 판단: 가장 최근 메일 기준이 "답장할 게 남았는지"를 가장 정확히 나타낸다)
  - 표시: 카드 상황 표시 "N일째 답장 안 함", 상세 안내 띠, 브라우저 알림 한 번
  - 끝나는 때: 답장 보냄(6단계), 닫기, 취소, 합쳐짐
  - **6단계 전까지의 한계 (사용자 결정):** Gmail에서 직접 답장해도 앱이 알 수 없어서, 답장한 업무에도 넛지가 남는다.
    - 이번 단계에서는 "답장했어요" 버튼을 따로 만들지 않는다. 사용자는 "답장 필요 없음으로 닫기"나 "나중에 보기"로 정리한다.
    - 6단계(보낸 메일 감지)에서 해결한다.
- **상대가 답장 안 한 업무 (6단계에서 연결)**
  - 조건: `WAITING`(답장 보냄) 상태로 **3일** 동안 상대 메일이 없다.
  - 동작: 업무를 "처리할 일"로 올리고 "상대 답장 없음 — 다시 연락할까요?" 안내를 띄운다. 선택지는 다시 연락하기(독촉 초안) / 완료로 닫기.
  - **상위 설계의 "답장 보냄 3일 후 자동 완료"를 이 동작으로 대체한다.** 상위 설계 4.9절을 고친다.
  - 이번 단계에서는 기준 값(3일)과 화면 부품만 준비한다.

### 4.3 업무 합치기
- **후보:** 새로 만들어진 메일 업무(합쳐지지 않음, 닫히지 않음)와 **보낸 사람 주소가 같고**, 처리할 일 · 답장 보냄 상태이며, **최근 14일 안에 만들어진** 다른 업무. 후보가 여러 개면 최근 것부터 최대 3개를 보여준다.
  - → 2026-10-27 변경: 후보는 ~~보낸 사람 주소가 같은 업무~~ → **같은 주소 또는 같은 회사 주소(무료 메일 도메인 제외)** 업무이고, 접수 분석에서 LLM이 관계와 근거 문장을 판단했을 때만 제안한다. 판별이 꺼져 있거나 분석이 실패하면 이 절의 "같은 보낸 사람" 규칙을 쓴다. 합치면 상대 요청 · 기한 · 요약은 아래 합집합 · 이른 기한 규칙 대신 재답장 분석으로 고친다(판별이 꺼져 있거나 분석이 실패하면 아래 규칙). 확정됨: [6단계 설계 7절](2026-10-27-reply-and-lifecycle-design.md#7-다른-스레드로-온-수정-요청-알아보기).
- **제안:** 새 업무 상세 맨 위 안내 띠 "김민수 님의 진행 중 업무가 있습니다: (업무 제목) [이 업무에 합치기] [따로 두기]". 카드에는 "합치기 제안" 표시를 붙인다.
- **"따로 두기"를 누르면** 그 업무에서는 다시 제안하지 않는다(`merge_dismissed`).
- **합치기 (새 업무 B → 기존 업무 A)**
  - B의 메일을 모두 A로 옮긴다.
  - B의 할 일을 A에 추가한다(중복 제목은 건너뜀). B의 상대 요청도 A에 추가한다(중복 제외).
  - B의 기한이 A보다 이르거나 A에 기한이 없으면 A의 기한을 B 것으로 바꾼다.
  - A의 중요도는 둘 중 높은 쪽으로 한다.
  - B는 `merged_into_id = A`, 상태 `COMPLETED`, 현재 단계 "업무 #A에 합쳐짐"이 된다. B에 캘린더 일정이 있으면 ✓를 붙인다.
  - A는 캘린더를 다시 반영한다. 두 업무의 타임라인에 "합침" 기록을 남긴다.
  - **이후 B의 스레드로 오는 메일은 A로 들어간다.** 접수 단계에서 스레드의 업무가 합쳐진 업무면, 합쳐진 대상을 따라간다.
- **되돌리기:** 합친 뒤 **10분 안에** A의 안내 띠에 "되돌리기" 버튼을 보여준다.
  - 누르면 옮긴 메일 · 할 일 · 요청을 원래대로 돌리고, B를 원래 상태로 복구하고, 기한 · 중요도도 합치기 전 값으로 돌린다.
  - 이를 위해 합칠 때 A와 B의 이전 값을 기록해 둔다.
  - 10분이 지나면 되돌리기는 사라진다.
  - **합친 뒤 A가 바뀐 경우 (내 판단): 옮겨 온 것만 되돌린다.**
    - B에서 온 메일 · 할 일 · 요청은 B로 돌려보낸다. 옮겨 온 할 일을 그사이 체크했다면 그 체크 상태를 유지한 채 돌려보낸다.
    - 합친 뒤 B의 스레드로 새로 들어와 A에 붙은 메일도 B로 돌려보낸다.
    - A의 기한 · 중요도는 **합친 뒤 사용자가 직접 바꾸지 않았을 때만** 합치기 전 값으로 돌린다. 직접 바꿨으면 그 값을 유지한다.
    - 사용자가 직접 한 수정을 되돌리기가 지우는 일은 없게 한다.

### 4.4 업무로 처리
- "업무 아님" · "자동 필터" 메일에서 누르면 그 메일을 `work`로 바꾸고 바로 접수 분석을 실행한다(3단계 `intake`를 사용자 요청으로 실행).
- **그 메일의 스레드에 이미 업무가 있으면 (내 판단)**
  - 새 업무를 만들지 않고 그 업무에 메일을 붙인다. 합쳐진 업무면 합쳐진 대상을 따라간다.
  - 그 업무가 완료 · 취소 상태면 "처리할 일"로 다시 연다. 상위 설계 4.6절의 "재답장 시 재오픈"과 같은 규칙이다.
  - 응답에 그 업무 번호를 돌려주고, 화면은 그 업무로 이동한다.
- 분석은 시간이 걸리므로 서버는 업무를 "분석 대기"로 즉시 만들고 응답한다. 분석은 워커가 이어서 처리한다(`wake`).
- 판별 스위치(`MAIL_TRIAGE_ENABLED`)가 꺼져 있으면 버튼 대신 "자동 판별이 꺼져 있어 분석할 수 없습니다"를 보여준다.

### 4.5 다시 분석
- 분석 실패(`brief.analysis == "failed"`) 업무에서 누르면 시도 횟수를 0으로 하고 "분석 대기"로 되돌린 뒤 워커를 깨운다. 3단계 `analyze_into_task`를 그대로 쓴다.

### 4.6 중요도 직접 변경
- 사용자가 바꾼 중요도는 `priority_source="user"`로 표시하고 이후 분석이 덮어쓰지 않는다.
- 업무의 `priority` 컬럼을 그대로 쓴다(`HIGH` / `NORMAL` / `LOW`).

## 5. 알림

- **브라우저 알림은 앱이 열려 있을 때만**이다. 서버 푸시는 하지 않는다.
- 1분마다 서버의 "알릴 것" 목록(`GET /api/inbox/alerts`)을 가져와 아직 띄우지 않은 것만 알린다.
- **알림 종류**
  - 기한 하루 전(오전 9시 이후)
  - 기한 당일(오전 9시 이후)
  - 스누즈 해제
  - 답장 넛지
- **한 번만 알리기:** 알림마다 고유 키(예: `deadline-d1:{task}:{기한 날짜}`)를 두고, 띄운 키를 브라우저 저장소에 기록한다. 기한이 바뀌면 키가 바뀌어 다시 알린다.
- **알림 문구:** "[D-1] A제품 100개 견적서 회신 요청". 누르면 그 업무를 연다.
- **탭 제목:** 지금 처리 건수가 1 이상이면 "(3) FollowUp Agent"
- **설정 화면:** "브라우저 알림 허용" 버튼과 현재 허용 상태. 거부됐으면 브라우저 설정에서 바꾸라는 안내.

## 6. 데이터 변경

`tasks`에 추가:

| 컬럼 | 설명 |
|---|---|
| `snoozed_until` | 스누즈 해제 시각 (UTC). 없으면 스누즈 아님 |
| `snooze_returned_at` | 마지막으로 다시 나타난 시각. "다시 표시됨" 24시간 표시용 |
| `priority_source` | `llm` / `user` |
| `merged_into_id` | 합쳐진 대상 업무 (자기 참조 외래 키) |
| `merge_dismissed` | 합치기 제안을 "따로 두기" 했는지 |
| `merge_undo` | JSON. 되돌리기용 이전 값과 합친 시각 |

- 상태값은 새로 만들지 않는다. "참고용"과 "분석 대기"는 3단계처럼 `PENDING` + `brief.analysis`로 구분한다.
- 마이그레이션은 SQLite와 PostgreSQL 양쪽에서 동작해야 한다.

## 7. API

모두 로그인 필요, 본인 업무만(아니면 404), 상태를 바꾸는 요청은 POST다.

| API | 하는 일 |
|---|---|
| `GET /api/inbox` | 탭별 업무 목록과 묶음 · 정렬 · 카드 표시 값, 요약 건수, 나중에 보기 목록, 업무 아님 목록 |
| `GET /api/inbox/alerts` | 지금 알릴 것 목록 (키, 종류, 업무 번호, 문구) |
| `POST /api/tasks/{id}/snooze` | `{until}` 또는 `{preset}` |
| `POST /api/tasks/{id}/unsnooze` | 지금 보기 |
| `POST /api/tasks/{id}/priority` | `{priority}` |
| `POST /api/tasks/{id}/deadline` | `{date, time?}` 또는 `{clear: true}` / `{confirm: true}` |
| `POST /api/tasks/{id}/todos` | 추가 · 체크 · 메모 · 삭제 (작업 종류를 본문으로 받음) |
| `POST /api/tasks/{id}/close` | 답장 필요 없음으로 닫기 `{reason?}` |
| `POST /api/tasks/{id}/merge` | `{into_task_id}` |
| `POST /api/tasks/{id}/merge/undo` | 10분 안에만 |
| `POST /api/tasks/{id}/merge/dismiss` | 따로 두기 |
| `POST /api/tasks/{id}/reanalyze` | 다시 분석 |
| `POST /api/emails/{id}/promote` | 업무로 처리 |

- 업무 상세 응답과 실시간 갱신(SSE)에 새 필드를 넣는다: 스누즈, 넛지, 합치기 후보, 되돌리기 가능 여부.
- 외부 서비스나 LLM을 부르는 API(`promote`, `reanalyze`)에는 호출 횟수 제한을 둔다.

## 8. 화면 원칙

- 기존 스타일(색 변수, 카드, 버튼)을 따른다. 새 색은 중요도 3색과 지난 기한 빨강뿐이다.
- 휴대폰 너비(약 400px)에서도 카드와 버튼이 한 줄로 쌓여 보여야 한다.
- 확인 단계는 화면 안에서 처리한다(`confirm` / `alert` 금지).
- 시안: `.superpowers/brainstorm/` 의 `inbox-layout-v3.html`(첫 화면), `inbox-layout.html`(업무 상세)

## 9. 상위 설계 문서에 반영할 것

- 4.9절: "답장 보냄 상태로 3일간 새 메일 없음 → 자동 완료"를 "3일 후 다시 연락할지 물어보기"로 바꾼다.
- 5절: 정렬을 2.2절 묶음 기준으로 바꾸고, 스누즈 · 넛지 · 합치기를 추가한다.
- 12.2절: "확정됨 — 이 문서 4.3절"로 표시한다. 12.1절(재답장으로 업무 갱신)은 6단계에 그대로 남는다.

## 10. 남은 위험

- **답장한 업무의 넛지 (6단계에서 해결):** Gmail에서 직접 답장한 업무에도 넛지와 알림(상대 메일당 한 번)이 남고, "답장 보냄" 탭은 6단계 전까지 비어 있다. 사용자가 받아들인 한계다(4.2절).
- **알림 누락:** 브라우저 알림은 앱이 열려 있을 때만 동작한다. 앱을 닫아 두면 캘린더 알림만 남는다. 서버 푸시는 실제 서비스로 열 때 다시 본다.
- **합치기 오판:** 같은 상대의 다른 건을 합칠 수 있다. 10분 되돌리기와 사람 확인으로 줄인다.
- **묶음 기준 조정:** "지금 처리"가 너무 길거나 짧으면 2.2절 기준을 실제 사용 후 조정한다. 기준 값은 설정으로 빼지 않고 코드 상수로 둔다.
- **기한을 없애도 캘린더 일정은 남는다 (6단계에서 결정):** 기한을 없앤 업무의 캘린더 일정은 지우지 않는다. 화면이 "캘린더 일정은 그대로 남습니다. 필요하면 캘린더에서 지워 주세요."라고 안내하고, 지우는 것은 사용자가 캘린더에서 한다.
