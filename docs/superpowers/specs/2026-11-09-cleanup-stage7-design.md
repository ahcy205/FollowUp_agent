## 2. `contacts`는 만들지 않는다 (사용자 결정 필요)
- 쓰려던 곳(목표 입력에서 받는 사람 고르기)이 없어졌다. 답장 받는 사람은 서버가 받은 메일에서 정한다.
- 만들면 메일 상대 주소를 따로 한 번 더 저장하게 되어 개인정보만 늘어난다.
- 상위 설계 7단계에서 지우고 `docs/decisions.md`에 남긴다. 나중에 "새 업무 직접 만들기"를 다시 만들면 그때 설계한다.

## 3. 유출 경고를 발송 전 확인에 넣는다
- '발송 전 확인'에 **스레드 밖 연락처** 줄을 더한다. 이 대화(보낸 사람 · 받는 사람 · 참조 머리글)에 없던 메일 주소 · 전화번호를 줄 안에 칩으로 보인다.
- 상위 설계대로 **경고만** 한다: 보내기를 막거나 체크를 요구하지 않는다. 그래서 막힘 · 확인 필요와 다른 "알림" 상태(황토 원 + 느낌표)로 보이고, 머리의 "확인할 것 n개"에는 세지 않는다.
- 같은 내용을 반복하던 초안 위 노란 상자는 고칠 수 있는 동안 숨긴다(다른 경고와 같게).
- 서버 · 저장 형식 · 보내기 규칙은 그대로.

## 4. 로그에 메일 내용이 새지 않게
- **DB 오류 메시지:** SQLAlchemy는 오류 메시지에 저장하려던 값(메일 본문 · 주소)을 붙인다. 이 메시지가 `log.exception`(처리 못 한 오류)으로 로그에 남을 수 있다. 엔진에 `hide_parameters=True`를 켜서 값 없이 남긴다.
- **회귀 테스트:** 메일 동기화 → 판별 → 접수 → 초안 → 보내기를 가짜 Gmail · 가짜 LLM으로 한 번 돌리고, 그동안 남은 로그(`logging`)와 처리 기록(`AgentActionLog`의 입력 · 결과)에 테스트 메일의 제목 · 본문 · 주소가 없는지 확인한다. 한 줄 요약(타임라인 허용)은 예외.
- 그 밖의 로그는 이미 메일 번호 · 건수 · 예외 이름만 남긴다(점검 결과).

## 5. 바꾸지 않는 것
- 보내기 규칙, API, DB 스키마(마이그레이션 없음), LLM 호출 · 프롬프트.
